## Conclusions

1. The two player scanners are already two different answers to "no engine". The web scanner has a standalone mode, chosen by the page's URL path. The ESP32 has none. Its "no engine" case is an outage path (queue, retry, "rescan later") that never ends. Decision 22's reasoning holds: this is a parity gap, and section 1.3 lists 24 differences.
2. Parity cuts both ways. In the 7 starred rows of section 1.3 the web scanner is the weaker one or the two are equally empty. A video token shows the web player a blank screen with the token id. Neither device records what players found. Neither shows which pack it carries. Matching the web scanner in those rows would copy a gap.
3. Standalone does not need the engine's hand-over of facts to the player devices, because player devices hold almost no shared facts. The seen list on the phone and the scan queue on the ESP32 are private to each device. So 7 of the 16 causes produce no fault on these two devices (C1, C2, C3, C5, C6, C8, C13).
4. The faults that do appear cluster in four places. A device cannot tell "no engine by choice" from "engine down" (C10, 8 findings counting D-11). The pack on each device is a hand-made copy and nothing checks it (C12, C14, C15, 7 findings counting D-19). Facts with no lifetime, the seen list and the scan queue, cross from one game to the next (C4, C9). And three duties the engine does today have no standalone owner, so devices drop them silently (new cause N1, 5 findings).
5. I propose one new cause, N1, and only one. The ESP32's missing standalone mode is not N1's reason, since decision 22 settles that as parity. N1 is about the game, not the device. Nothing in a game says "this game runs without an engine", and nothing says which engine duties it does without.
6. The first candidate design for 7 of the 16 causes works unchanged when no engine is present (C2, C3, C5, C6, C8, C11, C13), and for 6 of those only because there is nothing on the player devices for it to touch. Seven work partly (C1, C4, C9, C10, C14, C15, C16) and two do not work at all (C7, C12). Most name the engine as the sender of a message or the holder of a record. Section 3 gives each one-line change.
7. Not verified: what the GM scanner does in standalone beyond what its CLAUDE.md says (another sheet owns it); whether GitHub Pages currently serves this repository; heap use on the ESP32; what `DisplayDriver::drawBMP` shows when a file is missing (the screen code says the driver shows its own message, `ALNScanner_v5/ui/screens/TokenDisplayScreen.h:147`).

## 1. The answers

### 1.1 The web player scanner in standalone mode today

**How the mode is chosen.** By the page's URL path, nowhere else. `OrchestratorIntegration` sets `isStandalone` when the path does not start with `/player-scanner/` (`aln-memory-scanner/js/orchestratorIntegration.js:33-34`). The same rule is written a second time as `scannerCore.isStandaloneMode` (`js/scannerCore.js:51-54`), which `app.js` uses to pick where to look for pack identity (`js/app.js:98-102`), and a third time in the config page's discovery code (`config.html:423`). No setting, no game record, no button changes it. The kit's own documents say the same (`aln-memory-scanner/CLAUDE.md:13,26`; root `CLAUDE.md:80`). The mode a phone ends up in is also decided by the URL on the NFC tag it taps. The tag-writer writes `{baseUrl}?token={tokenId}` (`ALN-TokenData/tag-writer.html:444`), and every built-in baseUrl is an engine address ending in `/player-scanner/` (`ALN-TokenData/shared/aln-tools.js:10,15,20`). Only the "custom" field points a tag at a standalone page (`shared/aln-tools.js:31-41`).

**Where the token list and the content come from.** Not from the active pack. In standalone there is no active pack, and the page reads its own copy, `./data/tokens.json` (`js/app.js:64`). That file is the nested submodule `aln-memory-scanner/data/`, pinned at `15d8d2e`, not at the `6f9bc30` that `ALN-TokenData` and `ALNScanner/data` carry (`git submodule status --recursive`). The two token files differ in one entry. `nat001` has the group `Marcus Mention (x1)` in the scanner's copy and `Marcus Mention` in `ALN-TokenData` (python comparison, 81 keys in each). The scanner's `data/` folder has no `game.json` and no `pack-manifest.json` (`ls aln-memory-scanner/data`: `CLAUDE.md`, `scoring-config.json`, `shared`, `tag-writer.html`, `token-checkin.html`, `tokens.json`). If `data/tokens.json` fails to load it tries `./tokens.json`, then an embedded one-token database holding `test_001` (`js/app.js:61-87,127-139`). Pictures and sounds come from the `image` and `audio` paths inside the token file (`js/tokenDisplay.js:38-46,58-59`), which point into `aln-memory-scanner/assets/`. That folder holds 127 BMP files of 230,454 bytes each (29.3 MB) and 3 audio files. None of the 81 tokens names an audio file, and 2 tokens (`kai001`, `rem001`) have a `video` and no image (python count of `data/tokens.json`). The service worker caches the token file network-first (`sw.js:104-122`) and each picture only after its first view (`sw.js:192-202`). Its install list holds only the shell and `placeholder.bmp` (`sw.js:5-25`).

**What it does with a scan.** `handleScan` lowercases and strips the id to `[a-z0-9_]` (`js/scannerCore.js:28-44`), looks it up in the page's own file and refuses an unknown id with a 3-second toast (`js/app.js:393-408`; `js/tokenDisplay.js:135-144`). `processToken` then skips the engine entirely when `isStandalone` is true (`js/app.js:434`), adds the id to a seen set if new (`:448-451`), shows the memory and writes the set to `localStorage` key `alnMemoryScanner` (`:195-215,463`). Nothing else is stored: no time, no team, no count. The seen set is never cleared by any code (`grep scannedTokens js/`: set at `:18,200`, added to at `:450`, read at `:210,495,528`).

**What the screen shows.** The welcome screen with "Start Scanning" and "Manual Entry" (`index.html:38-52`). A known token fills the screen with its picture and a status line, "New Memory!" or "Memory Revisited", that fades after 4 seconds; a tap anywhere continues (`js/tokenDisplay.js:24-32`; `js/app.js:246-248`). Audio autoplays when the token has an `audio` path, with a tap-to-play fallback (`js/tokenDisplay.js:93-113`). A token with no image and no audio shows only the status line plus "Token: id" (`js/tokenDisplay.js:66-68`), which is what both video tokens get, because the web scanner never reads `processingImage` (`grep processingImage js/ sw.js index.html config.html`: no match). The header pill reads "Offline" for the whole session (`index.html:23-27`), because only the connection monitor repaints it (`js/app.js:595-603`) and the monitor never starts in standalone (`js/orchestratorIntegration.js:36-64`).

**What it lacks for a standalone game.**

- No record of what players found. Only a private seen set, with no time or team (`js/app.js:208-215`).
- No pack identity. The standalone path asks for `./data/pack-manifest.json` (`js/app.js:100-102`), which does not exist in the nested folder.
- No video. A video token shows only its id (above).
- Full offline play only for tokens already viewed. An unviewed picture falls back to `placeholder.bmp` (`sw.js:209-213`).
- A first load needs the internet. The page itself comes from GitHub Pages (`aln-memory-scanner/CLAUDE.md:13`; current Pages state not verified), and the QR library loads from `unpkg.com` (`index.html:138`; `sw.js:27-30` caches it only if the first load had internet).
- A seen set that never resets between games (`js/app.js:195-215`).
- A config page that offers to set an orchestrator the page will never use (section 2, SP-04).

### 1.2 The ESP32 with no engine reachable today

**Boot.** In order, from `Application::setup` (`ALNScanner_v5/Application.h:1570-1656`):

1. Display, then SD card (`:838-877`). No SD card ends `setup` here (`:1591-1594`).
2. Config load from `/config.txt` (`:1598`). The config needs `WIFI_SSID`, `ORCHESTRATOR_URL` and a 3-digit `TEAM_ID`, or `validate()` fails (`services/ConfigService.h:322-324,341-358,360-382`; `models/Config.h:30-72`). On failure `setup` logs "using defaults", keeps whatever fields parsed, and goes on (`Application.h:1598-1600`). No defaults exist for those three fields.
3. A 30-second serial override window, every boot unless `DEBUG_MODE=true` is already set (`Application.h:765-829`; the loop ends early only if a character arrives, `:791-798`).
4. Touch, audio, RFID (`:882-924`). RFID starts here, but the main loop does not run until `setup` returns.
5. Services (`:930-1053`). Queue file check (`:949-962`). WiFi, a wait of up to 10 seconds (`services/OrchestratorService.h:97-103`); with no SSID it skips WiFi (`:69-72`). If WiFi connects, one health check runs inside `initializeWiFi` (`:128`), and `checkHealth` retries 6 times with waits of 1, 2, 4, 8 and 16 seconds and a 5-second timeout each (`:341-347,1019-1052`), about 61 seconds when the engine is absent (arithmetic; the map says the same, `2026-10-30-map-clients-tests.md:110`). So a WiFi-up, engine-absent boot takes about 30 + 61 seconds before tokens load, plus the 10-second WiFi wait when the access point is also missing. With no access point the 30 and 10 seconds still apply.
6. Token sync runs only when the engine answered (`Application.h:978`). Otherwise the screen prints "Tokens: Cached" (`:991-995`) and the device loads `/tokens.json` from the SD card (`:997`). Asset sync likewise prints "Assets: Cached" (`:1007,1042-1046`).
7. Serial commands, background task, UI, Ready screen (`:1621-1651`).

**Where the token list, pictures and sounds come from.** The token list is `/tokens.json` on the SD card, and the device reads only `video` per token (`services/TokenService.h:93-146`). The file must have a top-level `tokens` object (`:125-129`). The only thing that writes it is the engine sync, which saves the body of `GET /api/tokens` (`:203-264`), an object `{tokens, count, lastUpdate}` (`backend/src/routes/resourceRoutes.js:57-61`). A fresh card from `sd-card-deploy/` holds one file, `assets/images/placeholder.bmp`. Pictures are `/assets/images/{id}.bmp` and sounds `/assets/audio/{id}.wav`, always built from the id (`models/Token.h:34-42`). Only the engine's asset sync fills them (`services/AssetService.h:90-224`). No other tool in the repository writes an SD card (`ls scripts/`; `ls arduino-cyd-player-scanner`). A card that never met an engine has no tokens, so every real scan shows "UNKNOWN TOKEN" (`TokenService.h:104-108`; `Application.h:542-547`).

**What happens to each scan.**

1. Tag read; failure shows "READ FAILED" or "COMM FAILED" for 1.5 seconds without blocking (`Application.h:505-531`; `config.h:41`).
2. Exact lookup of the raw text in the token list; a miss shows "UNKNOWN TOKEN" (`:539-548`; `TokenService.h:160-167`).
3. Not connected, which is every scan with no engine, so the scan goes straight to the queue (`Application.h:570,579-583`). If WiFi is up and the engine is not, the state is `ORCH_WIFI_CONNECTED`, which also queues (`OrchestratorService.h:1289-1313`).
4. The queue is `/queue.jsonl`. At 100 entries the oldest is dropped, silently (`:256-307`, `:263-265,1243-1247`; `config.h:63-67`). A queue file over 100 KB is deleted at boot (`OrchestratorService.h:427-443`). The queue survives reboots (`:445-458`). With no engine nothing reads it except the serial command `SHOW_QUEUE`, which prints the first 10 (`Application.h:1347-1350`).
5. The background task polls health every 10 seconds, each poll up to about 61 seconds when WiFi is up and the engine absent (`OrchestratorService.h:1266-1314`). It does nothing when WiFi is down.
6. The timestamp on each queued scan is a 1970 placeholder counted from boot, because NTP is requested only after WiFi connects (`Application.h:661-671`; `OrchestratorService.h:120`).

**What the player sees.** A known non-video token shows "Token Scanned:" and the id for 1 second (a blocking delay), then the picture and, if `/assets/audio/{id}.wav` exists, the sound, until a double-tap (`ui/screens/TokenDisplayScreen.h:133-136,141-166`; `ui/UIStateMachine.h:364-376`). The player cannot tell the scan was queued rather than recorded (`Application.h:579-597`; analysis D-17). An unknown token shows "UNKNOWN TOKEN" for 1.5 seconds.

**Video tokens.** The token's picture shows for 2.5 seconds with the overlay "VIDEO UNAVAILABLE" and "Rescan later" (`Application.h:586-593`; `config.h:40`; `ui/screens/ProcessingScreen.h:88-89,158-187`). Rescanning never helps with no engine.

**The status screen.** On a single tap it shows "WiFi: DISCONNECTED" in red or the SSID in green, "Orchestrator: OFFLINE" in red or orange, the queue count with "FULL" in red at 100, team and device ids (`ui/screens/StatusScreen.h:153-192`; wired at `Application.h:1636-1649`). It has no pack line and no word for "this game has no engine".

**Does any setting turn the engine off?** No. `SYNC_TOKENS=false` and `SYNC_ASSETS=false` skip the two syncs (`Application.h:978,1007`; `services/ConfigService.h:162-169`). They leave WiFi, the health poll, the queue and the retry loops running. `DEBUG_MODE` only defers RFID (`Application.h:901-920`). The config validator requires an orchestrator URL (`ConfigService.h:341-344`). A blank URL makes `validate()` fail, and the device then keeps running as the "using defaults" case with no engine, by accident, not design (`Application.h:1598-1600`; `OrchestratorService.h:200-204,342`).

**Cause note, N1 (candidate, not decided; the owner decides whether it is a seventeenth cause).** Deployment mode is a fact nobody holds. The web scanner infers it from a URL (SP-01), the ESP32 does not know it exists (SP-11), the NFC tag fixes it by the address written on it (SP-02), and no game record says which a game runs. Because nothing says what a standalone game does without, each device silently drops what the engine did, the record of player discoveries (SP-05), the video on a TV (SP-06), and the retry machinery runs for a service that was never meant to answer (SP-17). I looked for a home among the sixteen first. C11 holds the web's three answerers but not the missing declaration, and C10 holds the screens that misread the situation but not the cause of the misreading. The engine already has the nearest idea: a service can be "dormant" with a stated door, meaning not installed tonight (CONTEXT.md section 5b; root `CLAUDE.md` on `dormancyService`). A candidate to look at is to let the game declare standalone as a profile with no engine equipment, so every engine duty reads as dormant by the same words, and each device shows its answer. This is not a reason the ESP32 needs a standalone mode. Decision 22 already settles that as parity, and section 1.3 is the parity list.
