## 2. Local causes

Each "other places" list was found by the search recorded with it and every place was read by me. Backend places are listed only where I read the lines; the backend sheet covers the rest.

### C-c1. Each tablet keeps its own list of claimed tokens, so it must hear about every way a claim can change

Findings behind it: C-04, C-29, C-30, C-31.

Design cause: the backend decides a claim and releases it on delete, on reset and when another station claims; the tablet holds a copy of its own that it adds to, unions into, and unmarks only on one error. It is correct only if every path that changes a claim also reaches that copy, and several do not.

Other places with the same cause (search: `grep -rnE "scannedTokens|uniqueTokensScanned|scannedTokensByDevice" ALNScanner/src aln-memory-scanner/js backend/src backend/public`, 11 files):
- `S/core/storage/NetworkedStorage.js:67-75,83-96,453-460`: the same copy saved to the browser per game session and rebuilt by union.
- `S/core/storage/LocalStorage.js:97-107,324-326`: the standalone copy, rebuilt from transactions on load and added to on each scan; delete removes the transaction but I did not find a removal from the Set (read `removeTransaction` region by the search hit; not verified line by line).
- `aln-memory-scanner/js/app.js:18,196-214,448-450`: the web player scanner's "seen" set, added to on each scan, saved to the browser, never cleared and linked to no game session.
- `B/models/session.js:186-190` and `B/services/transactionService.js:695-722`: the backend's own counters `totalScans` and `uniqueTokensScanned` are incremented on accept and untouched when a delete frees the claim (the claim registry is spliced, the counters are not).
- `S/network/networkedQueueManager.js:132-149`: the queue's removal of "already recorded" entries is a second copy of the same claim, cleared by a different rule.

Candidate design choices (candidate, not decided):
1. The tablet shows the backend's claim list plus only its own offline scans the backend has not yet confirmed; the backend sends the list on every snapshot and on every claim change.
2. The tablet holds no claim list: the gate asks the backend each time the connection is up, and uses a short offline list only while disconnected.

### C-c2. Copies are rewritten by different rules for the same message and carry no age

Findings behind it: C-01, C-02, C-03, C-22, C-37, C-46.

Design cause: the tablet's copies are updated by replace, merge, add-if-absent, union or per-record overwrite, chosen separately for each copy, and none records when it was last confirmed. A copy cannot show that it is old, and a snapshot can only repair a copy whose rule happens to fit.

Other places with the same cause (search: `grep -rnE "backendScores\.set|this\.devices\.push|\.teams\.set\(|transactions = |_state\[domain\]|\.\.\.this\.sessionState" ALNScanner/src`, then the browser scanners):
- `S/core/teamRegistry.js:160-190`: clear and refill, ignored on a null session.
- `S/admin/MonitoringDisplay.js:265-270,353-358`: device list, add-if-absent and replace.
- `S/core/storage/NetworkedStorage.js:29-33,357-369,410,466-479`: transactions, scores and player scans each with their own rule.
- `aln-memory-scanner/js/orchestratorIntegration.js:187,373`: the web player scanner saves its whole offline queue and a pending batch by rewriting the whole value.
- `arduino-cyd-player-scanner/ALNScanner_v5/config.h:64-67`: the hardware scanner's queue file with a count cap and a corruption size threshold, a third rule.
- `backend/public/scoreboard.html:869,1294-1302,1477,1731,1760`: the wall scoreboard's evidence table uses add, delete by owner and clear at a snapshot or a new game session id.

Candidate design choices (candidate, not decided):
1. One write rule for every copy: replace by a full record carrying a version or time, with a visible stale mark when the time passes a limit.
2. Keep two rules only: replace for facts the backend owns, and "pending local action" for the tablet's own unconfirmed scans, each with the age shown.

### C-c3. The same question is answered from several copies, or recomputed on the tablet, so screens disagree

Findings behind it: C-06, C-21, C-24, C-25, C-26, C-28.

Design cause: no rule says which copy answers a question. Each screen reads whichever copy its author reached, or computes the figure itself when a lookup fails, so two screens of one tablet can show different totals, teams, statuses or ids.

Other places with the same cause (search: `grep -rnE "calculateTokenValue|getTeamScores|backendScores|getCurrentSession|currentSessionId" ALNScanner/src`):
- `S/ui/uiManager.js:473` and `S/ui/renderers/GameOpsRenderer.js:299`: points recomputed from the tablet's own table on the result screen and on every token card, even when the transaction carries `points`.
- `S/core/storage/NetworkedStorage.js:194-210` (scoreboard reads the backend scores) versus `S/core/unifiedDataManager.js:685-741` (team details computes locally).
- `S/ui/renderers/GameOpsRenderer.js:78` (scoreboard token count from the backend's figure) versus the token list on Team Details.
- `S/admin/MonitoringDisplay.js:38` and `S/ui/renderers/VideoRenderer.js:34`: two display-mode copies.
- `backend/public/scoreboard.html:869`: the wall scoreboard keeps its own score table for the same teams (read at its state block).

Candidate design choices (candidate, not decided):
1. Name one authoritative record per question on the backend and have every screen read only that record; the tablet may show a local figure only when labelled as pending.
2. Keep one read function per question inside the tablet (one place that answers "team score", "may I scan") so screens cannot choose a copy.

### C-c4. Modules, page elements, events and contracts are joined by loose names and shapes with no check, so a mismatch fails silently

Findings behind it: C-12, C-14, C-15, C-53, C-54.

Design cause: calls go through optional chaining and string names (a facade field that the strategies do not hold, a wrapped token read as the token, an element id, an event name, a message name) and an absent target is treated as "nothing to do". A wrong name never fails; it silently falls back.

Other places with the same cause (searches: the script comparing `getElementById('…')` ids with `ALNScanner/index.html` ids and template ids in `S/`; `new CustomEvent('…')` names against `addEventListener('…')` names in `S/`):
- `S/ui/uiManager.js:227` (`modeText`) and `:277` (`teamDisplay`): looked up, defined nowhere (read; both null-guarded, so they silently do nothing).
- `S/admin/MonitoringDisplay.js:402` (`orchestrator-status`) and `S/ui/renderers/VideoRenderer.js:17` (`video-status-badge`): defined nowhere.
- Events sent and never heard (search result): `initialized`, `player-scans:synced`, `session-state:updated`, `session:error`, `session:updated`, `settings:changed`, `settings:loaded`, `settings:saved`, `socket:connected`, `team:added`; heard and never sent: `game-state:updated`.
- `S/ui/renderers/GameOpsRenderer.js:352` reads `token.rfid` and `:221` reads `backendScores` off the facade.

Candidate design choices (candidate, not decided):
1. A start-up and test-time check that every looked-up id, listened event and subscribed message has exactly one definition, and that a missing one throws.
2. Typed interfaces between the facade and the strategies (one declared method list) so a strategy missing a method fails at load.

### C-c5. The tablet applies its own copy of the rules and shows its answer, in networked mode before the backend's verdict and in standalone mode instead of it

Findings behind it: C-07, C-09, C-10, C-11, C-19, C-41, C-56, C-57, C-58.

Design cause: the scanner carries its own implementation of scoring, group completion, the scan gate, token matching, naming and evidence filtering, kept in step with the backend's by hand and by comment. Where the two differ, the tablet's answer is shown first or alone.

Other places with the same cause (search: `grep -rnE "isScoringMode|isConsumingMode|calculateTokenValue|findToken|checkDuplicate|pointsFor" ALNScanner/src aln-memory-scanner/js arduino-cyd-player-scanner/ALNScanner_v5 backend/public`):

Candidate design choices (candidate, not decided):
1. Networked mode shows only the backend's verdict (a pending state until it arrives); standalone is the one place the tablet decides, from a shared rules module that the backend also loads.
2. Share one rules package between backend and tablet (the `gameRules` modules compiled for the browser) and run a parity test on both.

### C-c6. Nothing says what a tablet does at each boundary, so each boundary clears whatever its author remembered

Findings behind it: C-05, C-08, C-13, C-16, C-18, C-27, C-36, C-38, C-39, C-40, C-49, C-59.

Design cause: game start and end, a new game session, a system reset, a reload, a reconnect and a pack change each have their own code path, written separately. No list says which copies each boundary clears, keeps or re-fetches, and no boundary tells the tablet to re-check.

Other places with the same cause (search: `grep -rnE "resetForNewSession|clearQueue|handleSessionBoundary|_reset\(|\.reset\(" ALNScanner/src backend/src/services backend/public`, then reading the hits):
- `S/core/unifiedDataManager.js:542-560`: new-game-session reset that leaves service panels, devices and the session record.
- `B/services/sessionService.js:503-556` (read): game end stops the clock and suspends the cue engine, then nulls the session; it clears no held items, queue or running cues (the list the backend sheet owns).
- `B/services/sessionService.js:104-112` (read): restart restores `session:current` with no status check.
- `aln-memory-scanner/js/app.js:195-215`: the web player scanner's seen list is not cleared on a new game on the same phone.
- `backend/public/scoreboard.html:1473-1486` (CHK): handles a new game session id; the tablet's equivalent is `S/network/networkedSession.js:246-259`.

Candidate design choices (candidate, not decided):
1. A written boundary table (for each fact and each copy: clear, keep or re-fetch at game start, end, system reset, restart and pack change), with one boundary message sent to every client and one handler per client that applies the table.
2. At every boundary the backend sends a fresh full snapshot and the tablet replaces everything it holds, so the table reduces to "replace all".

### C-c7. Replies are matched by loose text or action name, and failures are read as temporary

Findings behind it: C-32, C-33, C-34, C-35, C-55.

Design cause: the tablet pairs a reply with a request by action name, a message prefix or the lack of a verdict, rather than a correlation id with a typed outcome. A repeated, late, failed or refused command is therefore misreported or replayed.

Other places with the same cause (search: `grep -rnE "gm:command:ack|clientTxId|NO-GO|startsWith\(" ALNScanner/src`):
- `S/network/orchestratorClient.js:189-242` (serialised by action; used only by `session:addTeam`).
- `S/network/networkedQueueManager.js:299-337`: replay matched by `clientTxId` (the one typed pairing), with a 30-second timeout that leaves the entry.
- `S/network/messageRouters.js:157-168`: an `error` event with `AUTH_` clears the token, while `CommandSender` ignores it.

Candidate design choices (candidate, not decided):
1. Every command carries a correlation id and every reply (ack, error, result) echoes it with a typed outcome; the tablet pairs only by id.
2. Keep action-name pairing but serialise same-action sends everywhere (as the one existing path does) and add typed fields for the outcomes that now travel as text.

### C-c8. A panel is drawn from one record that lacks facts needed to judge it

Findings behind it: C-43, C-47, C-48.

Design cause: each panel gets one service's record. The facts that decide whether the panel can be trusted (health, last check time, whether the profile loaded, which of a cue's commands are skipped) live in other records, so the panel cannot say "this is down", "this is old" or "half of this will not happen".

Other places with the same cause (search: `grep -rnE "connected|available|lastChecked|dormantCommands|disabledBy" ALNScanner/src/ui/renderers ALNScanner/src/admin`):
- `S/ui/renderers/EnvironmentRenderer.js:89-93`: lighting tiles drawn from the lighting record only.
- `S/ui/renderers/HealthRenderer.js:73-86`: summary built from health alone.
- `S/ui/renderers/MusicRenderer.js:114-116`: music panel drawn from the music record, which holds its own connected flag.
- `S/admin/MonitoringDisplay.js:296-308`: "Return to Video" built from two records.

Candidate design choices (candidate, not decided):
1. One record per service that carries both its health and its state, pushed together.
2. Keep two records but have the tablet join them in one read function, so a panel is never drawn from one alone.

### C-c9. Snapshot and live update of one fact have different shapes, so each screen carries its own adapter

Findings behind it: C-23, C-44, C-45, C-51.

Design cause: the backend builds the snapshot and the live push by different code, with different keys, filters and wrappers; the tablet adapts each at the point of use, and an adapter drops what it does not name.

Other places with the same cause (search: `grep -rnE "payload\.(session|devices|displayStatus|heldItems|gameClock|cueEngine)|mapVideoState|store\.(replace|update)" ALNScanner/src`):
- `S/network/messageRouters.js:125-144`: ten hand-keyed snapshot-to-domain mappings.
- `S/admin/MonitoringDisplay.js:105-112,180-188`: the video and clock adapters.
- `backend/public/scoreboard.html:1741-1789` (read by CHK, not re-read): the wall scoreboard reads none of the display snapshot.

Candidate design choices (candidate, not decided):
1. One builder per fact on the backend, used for both the snapshot and the push, with identical keys.
2. The tablet holds one domain object per fact and never reshapes it; screens read the domain object directly.

### C-c10. Reads are open by default, and each client picks the public read that suits it

Findings behind it: C-20.

Design cause: HTTP reads answer anyone and the credential check is optional per route; the tablet's naming, reload check and pack load are built on those open reads, so closing a route breaks its own clients.

Other places with the same cause (search: `grep -rnE "fetch\(" ALNScanner/src aln-memory-scanner/js backend/public/scoreboard.html`): `aln-memory-scanner/js/orchestratorIntegration.js:426` (`/health` with a device id registers a device), `backend/public/scoreboard.html:1493` (`/api/tokens`), `:1231` (`/api/pack/files/game.json`).

Candidate design choices (candidate, not decided):
1. A read tier per route: public (health, pack), station (state, session, tokens), with the station reads taking the same token the socket uses.
2. Move station naming and session checks onto the socket handshake so the HTTP reads can close.

### C-c11. Documents and records describe the scanner from memory and nothing checks them against the code

Findings behind it: C-17, C-50.

Design cause: the scanner's documents, comments and contract notes are written by hand after a change and never compared with the code, so they keep describing removed behaviour.

Other places with the same cause (search: `grep -rn "Last verified" ALNScanner/CLAUDE.md CLAUDE.md backend/CLAUDE.md`, then spot reads): the root `CLAUDE.md` section "Contract-First" and `CONTEXT.md` section 4 (self-heal line, C-08); `ALNScanner/CLAUDE.md` initialization and debugging sections (C-17).

Candidate design choices (candidate, not decided):
1. Machine-check the named files, lines, keys and events in the scanner's documents in the test run.
2. Remove the hand-written duplicates and point to the code or contract as the single record.

### C-c12. Status and phase words are compared as literals where used

Findings behind it: C-42, C-52.

Design cause: each site that needs to know a phase or health word lists the ones it knows ("paused", "active", "healthy"), so a site that forgets one treats it as the default.

Other places with the same cause (search: `grep -rnE "status (===|!==) '|\.status == '" ALNScanner/src`): `S/app/domains/gameOps.js:235` (`!== 'active'`), `S/core/storage/LocalStorage.js:302` (`=== 'paused'`), `S/network/messageRouters.js:198` (`!== 'ended'`), `S/ui/renderers/HealthRenderer.js:73-80`.

Candidate design choices (candidate, not decided):
1. One module exports the phase and health words with a helper for each decision ("may scan", "is live"), and no site compares a literal.
2. Send the decision from the backend ("scanning allowed: yes/no, reason") and let the tablet display it.
