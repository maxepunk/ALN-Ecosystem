Engine Architecture Plan

The game happens in a room. The engine connects a touch on a physical token to a response in the room and a fact on the record, lets staff run a session, and gives the people who make a game their tools. This plan is about the code structure that work stands on.

The engine's rules and its pack format are sound. The weak spots are in the plumbing the parts share: how a game's facts are decided and reach screens, how a request is answered, how the room's gear is driven, how a game moves through its life, and how one copy of the engine stays clear of another. Seven improvements fix those, and the rest of the rebuild stands on them.

They are judged by what the engine is meant to become: a platform for other people's games, at any size of install, for one night or a run of months. They are not a list of ALN's bugs.

What is already sound, and stays

  • The pack, and the check at start-up that refuses a bad pack.
  • The rules on the show machine, written as plain functions that are easy to test.
  • The comparison of what the show needs with what is installed, with its three words: healthy, down, and not installed here.
  • Pack delivery to devices, each showing which pack it holds.
  • Draft and publish in the design tool.
  • The toy game, and the rule that every change passes with both games.

The seven improvements

Each one says what is wrong in the structure today, what would change, and what that gives you at a session and for the work still to come. All seven carry my strongest recommendation.

1

The game's facts live in one place and reach every screen one way

Strong

Today

The show machine decides a scan
live updates are built by one piece of code
a reconnecting screen is caught up by another
GM tablet: has already marked the token, and keeps its own listsWall display: gets everything and filters it in the page

A fact present on one path and missing on the other has happened four times.

Proposed

One game record decides and holds every fact
one way out: the same code live and after a reconnect, each fact dated, filtered for each screen
Every screen draws what it is sent
At a session
What one GM did is what every tablet and the wall display show, also after a reconnect. A delete or a reset clears every screen. A tablet that loses the show machine keeps working and settles up when it is back.
For the rebuild
Capture, the night's record, players' phones and the second game's hidden facts each need one home for a fact and one filtered way out.

The order I would work in

  1. Now, with no design question open: improvement 6. It is small, and it makes testing on a real machine safe.
  2. The centre, as one thin slice from end to end: one scan through the one door (4), into the record (1), out to a tablet and the wall display (1), in the published form (3), with the table's rows for start and end (7), proven with both games.
  3. Then widen: the rest of the facts, the rules on the tablet (2), and the gear's interface and supervisor (5), where the paused hardening work continues.

Smaller ones, worth exploring

  • The design tool asks the engine through the same door. Today it writes the engine's files and loads the engine's code directly, and a published change shows only at the engine's next restart.
  • What is installed on a machine becomes one described set that the engine checks at start: engine version, apps, pack, media and profile. Today these are separate checkouts and hand-copied media that nothing compares.
  • The wall display becomes a screen like any other. This follows from 1 and 2.

What I need from you

Which of these do you want to look at closely? I recommend starting with 1, the game's facts, because 3, 4 and 7 take their form from it. We work through the one you pick in conversation, and what we decide goes into short decision notes and the revised roadmap.

Improvement 6 needs no decision. I can start it when you say so.
