A proposal for your review · 10 November 2026

Engine architecture plan

I went through the engine's code looking for places where the way it is organised will make the rest of the rebuild harder. This page proposes seven changes to how the code is organised. None of them changes ALN's rules or content.

  1. 1The backend keeps one complete record of each session, and updates every screen from it the same way.
  2. 2A standalone game runs the same game code as a networked one.
  3. 3The messages between the backend and the devices are defined in one place and checked automatically.
  4. 4Video, music, sound and lights are controlled through one pattern, and their programs restart when they crash.
  5. 5The engine keeps separate what belongs to one session, to one installation and to the whole production.
  6. 6The code has a known place for adding a new kind of rule, equipment or screen.
  7. 7The backend is assembled in one place, and a copy started for a test or a rehearsal leaves the installed backend as it was.

The game itself happens in a room, with players, token objects and GMs. The engine is the software around it. Its game rules and its pack format are in good shape. The weak spots are in how its programs work together, and that is what the seven changes are about.

I judged each change by what the engine is meant to become: open-source software that runs other people's games as well as ALN, on a kit as small as player scanners and tokens or as large as ALN's, at one venue for months or on tour. Three separate reviewers checked my first draft against the code. This version includes their corrections and your eight comments of 12 November.

How ALN runs while this work is done

Every ALN session runs on blue: the backend computer in use today, with its scanners and its production branch. This work never touches them. Nothing from the new engine reaches a live session until all of it is finished. Then there is one cutover: green, the second backend computer, replaces blue, and the hardware scanners get their new firmware.

So no part of the new engine has to work with an old part, and the order of work is set by engineering reasons alone.

Words used on this page

Game. A designed game, such as ALN. Session. One group of players playing it once.

Pack. The data files that define one game: token data, rules, text and cues. A token is a physical object with an NFC tag. The tag holds only an id, which points to that token's entry in the pack.

Kit. The physical gear a production owns: token objects, scanners, GMs' phones or tablets, a router, and optionally a computer for the backend, a TV, speakers and lights.

Installation. A kit set up at one venue, for one night or for months. Many sessions are played on it. The installation profile is the file that describes it.

Production. One game being run by its makers, at one venue for a long stay or on tour.

Backend. The engine's central program. In ALN it runs on a Raspberry Pi connected to the TV and speakers. A networked game uses it. A standalone game has no backend and runs on scanners alone.

Engine. The software that is the same for every game: the backend, the GM scanner, the player scanners (the web page on a phone and the hardware scanner), the scoreboard and the config tool.

What is already in good shape, and stays

  • The pack format, and the check at start-up that refuses a pack the engine cannot run.
  • The game rules in the backend: scoring, duplicates, group bonuses. They are self-contained and easy to test.
  • The comparison of what a game needs with the gear that is installed, and its three words: healthy, down, dormant.
  • The way the state of video, music, sound and lights reaches the GM scanner: one kind of message for all of them.
  • Draft and publish in the config tool.
  • The toy game, and the rule that every change must pass with both ALN and the toy game.

Two limits on that list. The toy game is the same kind of game as ALN and has no media, so passing with both does not prove the engine suits other kinds of game. And the phone's player scanner loads its own copy of the token data but displays the backend's pack version.

The seven changes

Each card says what happens today, what I propose, what you would notice at a session, what later work it makes possible, and what it costs. I recommend all seven. The sixth is a rule for designing the others more than a separate piece of work.

1

The backend keeps one complete record of each session, and updates every screen from it the same way

Recommended

Today

A player scanner's scan, a GM scanner's scan and a GM's command each reach the backend through a different entry point, with its own checks and its own kind of reply. There are six entry points
The backend keeps the session's current data: the list of transactions and the scores. Deleting a transaction removes it from the list, and resetting the scores empties the list. The session's data then shows no sign that either happened
The GM scanner marks a token as used as soon as it is scanned, before the backend replies, and keeps its own copy of the transactions and scores
One piece of code updates a GM scanner that stayed connected. A different piece brings a reconnecting one up to date

Four times so far, that second piece has left something out. Separately, any device on the kit's Wi-Fi can read the scores and the whole pack without identifying itself.

Proposed

Every scan and command reaches the backend through one entry point and gets one kind of reply: accepted, refused with the reason, held for later, or failed and worth retrying. The reply also says what the device should show
The backend keeps a record that only grows. Every scan, delete, score change and reset is added as a new line, in order. The scores and everything on screen are worked out from it
In a networked game, only the backend decides whether a scan counts. One piece of code updates every screen, connected or reconnecting

What each kind of device may do is set in the pack. Three things always stay with staff: starting and ending a session, controlling the show, and changing scores. "Player scanners only view, GM scanners score" is ALN's choice, not the engine's rule.

At a session
What a GM does on one GM scanner appears on every other GM scanner and on the scoreboard, including after a reconnect. Every tap gets a clear reply. Scans taken without a connection are added in the right order when it returns.
Later work it allows
Staff notes and photos during a session. A full record of each session for the report. Players tapping tokens with their own phones. Actions made of several taps in a row, which the second game needs. Games that show different players different things.
What it costs
It is the biggest of the seven, because every scan and command passes through this code. And for the backend to check what a player scanner may do, each one would need a credential, issued automatically with no login. None has one today, and the roadmap leaves that decision to you.

Decided on 13 November. The record only grows. A delete is a new line saying "this transaction was deleted", and nothing changes or removes a line once it is written. The alternative was to keep editing the session's data in place, as today.

2

A standalone game runs the same game code as a networked one

Recommended

Today

Networked. The backend decides what each GM scan does: whether the token is already used, what it scores, whether it completes a groupStandalone. The GM scanner decides, with its own separate copy of those rules and its own way of storing the session
the two copies are kept the same by hand, with code comments and tests whose expected results are typed in

They already differ. A standalone GM scanner accepts scans before a session starts and after it ends. The backend refuses both. Across the scanners and the scoreboard, sixteen rules are written a second time like this, and for five of them nothing checks that the copies agree.

The installation profile can say that an installation has no backend, but only the backend reads that file. The GM scanner goes by a button the GM taps at start-up, and the phone's player scanner by the web address it was opened from.

Proposed

The code that decides what a scan does and keeps the session's record is written once
the same code runs in both places
in the backend, for a networked gameinside the GM scanner, for a standalone game

Whether a game is standalone or networked is declared in one place that every device reads.

At a session
A standalone game scores, refuses duplicates and completes groups exactly as a networked game does, because it is the same code.
Later work it allows
Games for places where a network is not feasible, or where it is simpler to bring only scanners. A new rule is written once and works in both.
What it costs
That code has to run in two places from the start: in the backend, and inside the GM scanner's web page. The two are in separate repositories today, so the shared code needs one place both can load it from.

A choice inside this one. The GM scanner can run all of that code, which I recommend. Or it can share only the scoring calculations and keep its own code for the rest. Or it can keep its own copy, with more tests comparing the two. Sharing only the calculations would leave most of the duplication, because most of the sixteen duplicated rules are not calculations. They cover things like when a scan is allowed and where one session ends.

3

The messages between the backend and the devices are defined in one place and checked automatically

Recommended

Today

Two files describe the messages that the scanners, the scoreboard and the backend send each other
some tests compare the programs with those files, but each program still has the message names typed into it by hand
BackendGM scannerPlayer scanner on a phoneHardware player scannerScoreboard

If the backend sends a message whose name is missing from the GM scanner's hand-typed list, the GM scanner ignores it and nothing warns anyone. When a device connects, nothing checks that it and the backend expect the same messages. And what is written onto a token's NFC tag is described in neither file.

Proposed

One definition, with a version number, of three things: every message, every file the engine reads or writes (the pack, the installation profile, a session's record), and what is written on a tag
every program is tested against it automatically whenever the program or the definition changes
The backend, the GM scanner, both player scanners, the scoreboard and the config tool

You decided on 1 November that the engine would have one published protocol. This is how I would build it. Testing every program against the definition comes first. Generating code from the definition can come later, where it saves work.

At a session
After a software update, a scanner that does not match the backend is caught when it connects, before the session starts.
Later work it allows
New kinds of device and screen. Software that other people write for the engine. Updating a pack at any time, while the engine's own software is updated only between events.
What it costs
The definition has to be written before the programs that use it, and each program's tests rewritten against it. The hardware scanners' firmware changes too, so they are re-flashed at the cutover. Nothing has to stay compatible with blue or its scanners, because the switch happens all at once.
Where this is in the code
  • backend/contracts/openapi.yaml, asyncapi.yaml (the two files)
  • backend/tests/contract/scanner/ (the tests that exist)
  • ALNScanner/src/network/orchestratorClient.js:26 (the GM scanner's hand-typed list of message names)
  • arduino-cyd-player-scanner/ALNScanner_v5/services/ScanResponse.h:41 (replies fixed in the hardware scanner's firmware)
  • ALN-TokenData/tag-writer.html (what is written on a tag)
4

Video, music, sound and lights are controlled through one pattern, and their programs restart when they crash

Recommended

Today

Video playerMusic playerSound effectsAudio routingBluetoothLightsScoreboard browser
the backend has seven pieces of code, one for each. They are alike, but each has its own differences

What a program is doing and whether it is working are reported to the GM scanner as two separate things, so the admin panel can still show a program's last known state after that program has stopped. And a player scanner that checks in before a session exists is not recorded, so nothing can count the scanners before a session.

If the backend itself restarts in the middle of a session, the session's data, the clock and the list of cues already fired come back. Much else does not. Every GM is logged out. Music stops and stays stopped. The TV goes back to the idle loop. A cue part-way through its timeline stops there. Held items are gone.

Proposed

All seven follow one written pattern. Each accepts commands, including "check this now", and gives one report: what it is doing, whether it is working, and when that was last checked
One part of the backend starts all seven programs, restarts any that crash, and stops them when the backend stops
A backend restart follows the same steps as a normal start, then puts the show back from the session's record. The GMs stay logged in. The TV and the music return to where they were. Anything that was cut off is offered to the GM, not replayed by itself
The backend knows which GM scanners, player scanners and displays are connected, whether or not a session exists

For a rehearsal with no real gear, the same seven programs run, connected to software that stands in for the speakers and lights. You already ruled that a rehearsal works this way, through an ordinary installation profile that points at stand-ins.

At a session
A crashed program restarts by itself. If it cannot, the GM scanner shows it in red with what to do. Gear that is not part of this installation shows grey. If the backend itself restarts, the show comes back to where it was, with nobody logging in again or setting things up again.
Later work it allows
The paused work on automatic restarts and the preflight is built once for all seven, not seven times.
What it costs
Seven pieces of code rewritten to the one pattern, one at a time. Putting the show back after a restart also needs the session's record (change 1) to hold what the show was doing.

Already decided, not a choice. You ruled on 12 September that the backend starts and supervises these programs itself, through one supervision path. That stands, and it is the sound choice: the backend is the only part that knows which programs this game and this installation need, and a restart then has one way back. My earlier version reopened it so that video and music could keep playing through a backend restart. That is not what goes wrong in a restart, and it is not worth a second way of recovering.

  • backend/src/middleware/auth.js:13 (GM logins kept only in memory); services/displayControlService.js:31; services/cue/timelineRuntime.js:63; services/heldItemsStore.js:40 (lost in a restart)

5

The engine keeps separate what belongs to one session, to one installation and to the whole production

Recommended

Today

The backend holds one session at a time. Five hand-written lists of steps say what to do when it starts up, shuts down or resets, and when a session starts, pauses or ends
GM scanners and the scoreboard work out that a new session has begun from a changed session id. Player scanners are never told

So the devices do not agree on where one session ends and the next begins. Scans that a player scanner stored while it had no connection can be added to the next group's session.

Facts about the installation are spread over several files, and the GMs' logins are kept only in memory, so restarting the backend logs every GM scanner out. Each device loads its copy of the pack when it starts, and is not told when the pack changes. A backend that restarts in the middle of a session picks up any pack edit made since the session began, with only a line in the log.

Proposed

One session. It is set up, started, paused and ended. Its record only grows. Notes can still be added after it ends
One installation. One place holds which gear is installed, which devices belong to it and are logged in, and the records of the sessions played on it. It survives restarts
The production. The pack, its versions and its media files are kept together, so one backend can hold more than one game
one table says what happens to each piece of data when a session starts, pauses, ends or is reset, when the backend starts or stops, and when a new pack is applied. One piece of code carries it out and tells every device. A session keeps the pack it started with
At a session
In a long run, "end this session, reset, start the next group" leaves every screen and every scanner clean each time. A restart in the middle of a session loses nothing. A touring game arrives at a new venue with one installation profile to fill in.
Later work it allows
Staff notes and photos. The venue technician's screens. More than one game on one backend. The designer's loop from the roadmap: change a value in the config tool, apply it, and playtest.
What it costs
Every device has to be told when a new pack is applied, and reload it. Today each loads its copy once, when it starts. This plan does not require the backend to change packs without restarting. The roadmap asks for that only to make the designer's loop fast, and whether a restart is fast enough can be settled when the config tool's editor is built.

  • backend/src/routes/scanRoutes.js:317 (stored scans added to the current session)
  • backend/src/middleware/auth.js:13 (GM logins kept only in memory)
  • backend/src/services/sessionService.js:113 (a restart under a different pack only logs a warning)

6

The code has a known place for adding a new kind of rule, equipment or screen

Recommended

Today

The engine has a list of its capabilities. A pack lists the capabilities it needs. At start-up the backend refuses a pack that needs one the engine does not have
that check works well. But adding a new capability means changing code in many places, with no pattern to follow
The session's data is built around ALN's kind of game: accounts, transactions, scoresThere is one way of scoring

Proposed

A new kind of rule, such as another way of scoring, is one new file in one known folder, written to a set pattern. A pack asks for it by name
A new kind of equipment is one new file written to the pattern in change 4
A new kind of screen is one new page that is told what to show, as in change 1

This matches the two kinds of extension you described on 2 November. A game's maker combines the engine's existing capabilities inside the pack, with no programming. A developer adds a new capability to the engine as one new piece of code, and then any game can use it.

For a developer
Someone adding a capability knows where the code goes and what it has to look like. A game that uses the capability proves it works.
Later work it allows
The ways the engine is meant to grow. The project's notes already list 28 of them, from a third way to turn in a token, to a different lighting system, to audio in several rooms. Two are your own examples.
How the places are designed
From the kinds of addition the engine is meant to allow, not from one game. Each place is checked against at least two different cases from that list, and against one test: what an addition must not need to touch. Today's scoring, the seven programs and the scoreboard become the first rule, the first equipment and the first screen, so no place is built on a guess. The second game is one case among the 28.
Where this is in the code

  • backend/src/gameRules/scoring.js; backend/src/models/session.js
  • docs/plans/architecture-pass/requirements/2026-11-01-extension-cases.json (the 28 ways the engine must be able to grow)

The backend is assembled in one place, and a copy started for a test or a rehearsal leaves the installed backend as it was

Recommended

Today

The backend is made of fourteen parts. The list of those parts is typed out by hand in about a dozen places. One of those lists leaves out the music
The backend assumes it is the only copy running on its computer. The automatic tests start a second copy today, and a rehearsal from the config tool would start one later. That copy uses the same thirteen temporary files, the same screen and the same video player as the installed backend

When any copy starts, it stops every scoreboard browser and every sound monitor on the computer, including the installed backend's. This is a risk between sessions, not during one. No real situation has a test or a rehearsal running in the middle of a live session.

Proposed

The backend is assembled in one place in the code, from one list of its parts
Each running copy keeps its files in its own folder and stops only the programs it started
Only one copy at a time uses the real TV, speakers and lights. A copy started for a test or a rehearsal uses stand-ins
Between sessions
A test run or a rehearsal on the backend's computer leaves the installed backend exactly as it was for the next session.
For development
A test can start the backend with only the parts it needs, and tests can run side by side. Today the integration tests have to run one at a time.
What it costs
Less than I first said. I have dropped two copies sharing the TV and the players at the same moment, because nothing needs it. What is left is one place of assembly, a folder for each copy, and stopping only what a copy started.

The order of work

You decided the order on 30 October and 1 November: design first and then build, and design the hardest things to reverse first. Each item below is built on the ones before it, so nothing is built twice.

  1. Design how the backend keeps a session's data (change 1), with what belongs to a session, an installation and a production (change 5). Everything else reads or writes this data, so it is the hardest thing to change later.
  2. Design the messages and files (change 3). They follow from how the session's data is kept, and every program is built and tested against them.
  3. Design which device decides what (change 2): in a networked game, in a standalone game, and on a GM scanner that has lost its connection. This says where the game code must be able to run.
  4. Design how the engine is extended (change 6), with the pattern for equipment (change 4) and how copies of the backend stay apart (change 7). These join the first three at a few points and are easier to change later.
  5. Decide how today's code moves to the new design: changed in place, or moved piece by piece into a new structure.
  6. Build a thin first version that works end to end: one scan, from the tap, into the session's record, and out to a GM scanner and the scoreboard, in the backend and inside a standalone GM scanner, across a lost connection and a restart.
  7. Build the rest one area at a time, each with its detailed design just before it is built. The paused work on automatic restarts and the preflight is rebuilt here.
  8. Cut over once, when you decide the new engine is ready. Green is set up and rehearsed at the venue before that.

The five design items are conversations with you, a few questions at a time, each with my recommendation. At the start of each one I say which decisions I need from you, so you can tell when it is settled. They end in short decision notes, not in more pages.

None of this is small. The backend and the GM scanner together are about 43,000 lines of code, with about 116,000 lines of tests that have to change with them. That is why the build goes in small pieces that each work.

One smaller change is also worth exploring. The config tool should send its changes to the backend as messages, the way the scanners do. Today it writes the engine's files and uses the engine's code directly. I would settle that when the messages are designed.

Where we are

Confirmed on 13 November: how ALN runs while this work is done, and the order of work.

How the backend keeps a session's data: settled. These were the decisions I needed from you, and you made them all on 13 November:

  • The session record only grows. A correction is a new line.
  • It holds the game, the capture, what the room did and what went wrong, with one line for each event a person at the session would recognise.
  • After a session ends, notes, photos and the accusation can still be added until the next session is created. Stored player scans that arrive late go into the session they were made in.
  • Between groups, everything the group's play produced is wiped and kept only in that session's record. Everything about the room stays. The pack belongs to the production.
  • Moving money between accounts becomes one action for the GM and one line in the record. It is built with the GM scanner's redesign.

Nothing more is needed from you on this. What is left of it is engineering detail, such as how the record is stored on disk, and that is mine to work out.

Now: the messages between the backend and the devices, and the files. Decided on 13 November:

  • A player sees the same thing after a scan on the phone page and on the hardware scanner. The memory appears at once, and it still shows when there is no session, with a notice.
  • A device says which pack and which version it has when it connects. A wrong pack fixes itself. A hardware scanner whose firmware is too old says so and shows red on the GM scanner.
  • The pack says what each kind of device is sent. For ALN, a player scanner gets each token's picture, sound and video name.

Still needed from you on this: three decisions. Each is in the chat of 13 November, with what I found and what I recommend. The two pieces of research are finished.

  • Credentials. Every device shows the backend a credential before it can read or send anything. Staff log in. The kit's own scanners and screens get theirs when they are added to the kit. A player's own phone gets one on its first visit, with nothing for the player to do, and it lasts for one session.
  • Firmware updates over the air for the hardware scanner. They are possible. Each scanner needs one more flash by USB first, and the cutover does that flash anyway. After it, a scanner fetches new firmware from the backend when it starts up, and never during a session.
  • What a tag holds. The token's id, and the web address of the phone page for that token. An iPhone opens the address when it touches a tag. An Android phone opens the phone page first and scans inside it, as it does today. Every reader in the engine finds the id wherever it sits on the tag, so each production chooses the order. ALN keeps the order it has.

With these three made, the messages and the files are settled. The next topic is which device decides what: networked, standalone, and a GM scanner that has lost its connection.
