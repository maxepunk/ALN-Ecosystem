Engine Architecture Plan

The game happens in a room. The engine connects a touch on a physical token to a response in the room and a fact on the record, lets staff run a session, and gives the people who make a game their tools. This plan is about the code structure all of that stands on.

The engine's rules and its pack format are sound. The weak spots are in what the parts share: how a request gets in, where a game's facts are kept, how they reach screens, how the room's gear is driven, and how long each fact is meant to last. Seven improvements address those, and the rest of the rebuild stands on them.

They are judged by what the engine is meant to become: a platform for other people's games, at any size of install, for one night or a run of months. They are not a list of ALN's bugs. Three independent readers challenged a first draft with the code in front of them. This version carries what they found.

What is already sound, and stays

  • The pack format, and the start-up check that refuses a pack the engine cannot run.
  • The rules on the show machine, written as plain functions that are easy to test.
  • The comparison of what a game needs with what is installed, with its three words: healthy, down, and not installed here.
  • The state of the room's programs, which already reaches the GM tablet one way.
  • Draft and publish in the design tool.
  • The toy game, and the rule that every change passes with both games.

Two limits on that list. The toy game is the same kind of game as ALN and has no media, so passing with both games does not prove the engine is general. And the phone still reads its own copy of the token data while showing the show machine's pack version.

The seven improvements

Each one says what is wrong in the structure today, what would change, what that gives you at a session and for the work still to come, and what it costs. Six carry my strongest recommendation. The sixth is worth exploring.

1

One way in, one record, one way out

Strong

Today

Six ways in, each with its own kind of reply
which way a device uses fixes what it may do
The record: one snapshot, rewritten. A delete or a score reset erases what happened
live updates and the catch-up after a reconnect are put together in different places
GM tablet: marks the token before the answer comes, and keeps its own listsWall display: gets everything and filters it in the page

Four times, a catch-up has left something out. Anyone on the kit's network can read the whole record and the whole pack without a pass.

Proposed

One door. Who is acting, and may they
every request gets one reply, which says what happened and carries what the device should show
One record that decides and keeps every fact of the game
one way out: each screen gets its own view, live or after a reconnect, each fact dated
Screens draw what they are sent

Who may do what comes from the pack, above a floor that stays with staff. “Players view, GMs score” is ALN's arrangement, not the engine's.

At a session
What one GM did is what every tablet and the wall display show, also after a reconnect. Every tap gets an answer the person can act on. A tablet that loses the show machine keeps working, and its scans join the record when it is back.
For the rebuild
Capture and the night's record, players' phones, scans of several objects, and a game that shows different players different things.
What it costs
This is the centre of the engine, so it is the largest piece. Every player scanner needs a pass, which none has today.

A choice inside this one. Keep the record as an ordered list of everything decided: each scan taken or refused, each delete, each reset. Every screen's view and the night's record are worked out from the list. Or keep only the current state, as today. I recommend the list. A tablet that was cut off adds its scans in order, a restart replays it, and nothing that happened is erased. All three readers pointed the same way.

2

The same core runs wherever a game is decided

Strong

Today

Show machine: door, record and rulesGM tablet: a second, hand-written engine for a game with no show machine
kept in step by comments and paired tests

Sixteen decisions are made a second time on devices. For five of them nothing checks that the copies agree. The install's profile can say a kit has no show machine, but only the show machine reads the profile. The tablet goes by a tap, the phone by its web address.

Proposed

The core from improvement 1, as one package that does not care where it runs
hosted by
The show machine, in a networked gameA GM tablet, when the kit has no show machine

Whether an install has a show machine is declared once, where every device can read it.

At a session
A kit with no show machine scores a game exactly as the full rig does. Records from tablets that ran alone can be joined afterwards.
For the rebuild
A touring game that plays with less gear, and every new rule, land once.
What it costs
The core must run in a browser as well as on the show machine from its first slice. The code lives in separate repositories today, so the core needs one home that both are built from.

A choice inside this one. The tablet hosts the whole core, which I recommend. Or it shares only the rule functions. Or it keeps code of its own that tests check. The readers were firm that sharing the rule functions alone leaves the second engine in place, because most of the repeated decisions sit in the record and not in the rules.

3

One published protocol

Strong

Today

Two contract files describe the messages
tests compare some programs against them when built; names are still copied by hand
Show machineGM tabletPhoneHardware scannerWall display

No version of the protocol is checked when a device connects. While a game runs, a message the tablet does not know is dropped without a word. What is written on a tag, which joins an object to its data, is in neither contract file. It lives in the tag-writing tool and the scanner's reader.

Proposed

One definition, with a version: every request, reply and fact; the pack, the profile and the night's record; and what is written on a tag
every program is checked against it when it is built
Every program and every device

You decided this on 1 November. Checking comes first. Making code from the definition can follow where it pays.

At a session
After an update, a device that does not match is found before the game, not during it.
For the rebuild
Every new device and screen, anyone else's extension, and packs that update at any time while the engine updates between events.
What it costs
While the old show machine stays the fallback, tablets and scanners must work with both.

4

One interface for the room's gear and the kit's devices

Strong

Today

VideoMusicSoundAudio routingBluetoothLightsDisplay
seven drivers that follow a pattern nobody wrote down, each with its own differences

A program's state and its health travel separately, so a panel can show a calm value for a dead program. When the engine restarts, it stops the video and the music with it. A scanner that checks in before a session exists is forgotten, so nothing can count the devices before a game.

Proposed

One written interface for each thing the room can do: commands in, with “try it”; state, health and age out together
the real program underneath, pointed at real gear or at stand-in gear by the install's profile
One way to keep the programs runningTablets, scanners and displays known to the install the same way, with or without a session
At a session
A crashed program comes back by itself, or the GM sees red with what to press. Gear that is not installed here shows grey. An engine restart does not blank the TV.
For the rebuild
The paused work on automatic restarts and the preflight lands once, not seven times. Rehearsing at a desk is the same engine and programs with a profile of stand-in gear, which the test rig already does.
What it costs
Seven drivers rewritten to one pattern, one at a time. No question of yours blocks it.

A choice inside this one. Who keeps the programs running. The show machine's own service manager, which I recommend there because video and music then survive an engine restart. Or the engine itself, which is easier to test and works on any computer. A one-day trial on the new show machine settles it.

5

Every fact has a stated life: a session, an install or a production

Strong

Today

Five hand-kept lists of steps: start-up, reset, shutdown, and what happens when a game starts, pauses or ends
tablets and the wall display guess that a new game began; player scanners are never told

Only one session exists at a time, and a phone's queued scans can land in the next group's session. Facts about the install sit in several places, and some live only in memory: a restart forgets a GM's “out of service” mark and logs every tablet out. Every holder of the pack fixes its copy at start-up, and nothing tells it the pack changed.

Proposed

A session. One group's game: set up, start, pause, end. Its record only grows, and stays open after “end” for notes
An install. What is set up at this venue, for a night or for months. One document: the gear, the devices, what is out of service, and past sessions' records
A production. The game over its whole life: the pack, its versions and its media, as one thing a kit can hold several of
one table says what each fact does at each moment; one piece of code moves a game along and tells every screen
At a session
On a long run, “end, reset, next group” leaves every screen clean each time. A restart mid-game loses nothing. A touring game arrives with one document to fill in.
For the rebuild
Capture, the venue technician's pages, several games on one kit, and applying a pack without a restart.
What it costs
Applying a pack without a restart is a large piece of its own, because every copy of the pack is fixed at start-up today.

Worth exploring

Proposed

This is your two kinds of extension. Combining what the engine already has is done in the pack, with no code. A new ability is one module at a marked place, and every game can then use it.

For extending it

For the rebuild
The second game's modules, and other people's games after release.
Why not “strong”
I would shape these from the second game's real taps, written first as test cases, and not from ALN alone.

Strong

Today

Fourteen parts each exist once, shared by the whole program

Proposed

One place builds a copy of the engine from one list of parts
each copy has its own names: files, ports, display, passes, programs
Each copy stops only what it started
At a session
Nothing run at a desk or in a test can interrupt a live game on the same machine.
For the rebuild

More than it looks. Beyond file names, two copies collide on the video player's name, on audio streams matched by program name, and on the one display. The trial in improvement 4 decides how much of this is left.

The order I would work in

  1. Start with the room's side: the gear (4), with one place that builds each copy (7). No question of yours blocks them, and the paused work on restarts and the preflight continues there. A one-day trial on the new show machine settles who keeps the programs running.
  2. Meanwhile, work through the core with you (1 and 2). Before it is built I write the second game's taps as test cases, so the core is not shaped by ALN alone.
  3. Build the core as one thin slice from end to end: one scan through the door, into the record, out to a tablet and the wall display. It runs on the show machine and on a tablet alone. The proof includes a player's device, a cut-off tablet and a restart. It uses the published form (3) and a session's start and end (5).
  4. Widen from there, adding the marked places (6) as the second game needs them.

Throughout, today's engine keeps running sessions, and the old show machine stays the fallback.

None of this is small. The show machine's program and the GM tablet's app are about 43,000 lines of code with about 116,000 lines of tests, and the tests move with every change. That is why the work goes in thin slices.

Smaller ones, worth exploring

  • The design tool asks the engine through the same door, before its pages are built. Today it writes the engine's files and loads the engine's code directly.
  • The wall display becomes a screen like any other. This follows from 1.

What I need from you

Which of these do you want to look at closely? I recommend the core, 1 and 2 together, starting with the choice inside 1. We work through it in conversation. What we decide goes into short decision notes and the revised roadmap.

May I start on the room's side, 4 and 7, meanwhile?

Three things this plan does not decide. They come up when we look at the core: what a GM may tell a team while a tablet is cut off, what a device that missed an update may do, and where a rehearsal copy may run while a session is live.
