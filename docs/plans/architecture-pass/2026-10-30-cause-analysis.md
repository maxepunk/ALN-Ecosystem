## 1. The causes in short

Sixteen causes, ordered by how much each affects a show night, most first. The first four hold the four reproductions the program document names for the rig (section 4.1, step 2): the deleted token still refused (C1), the music panel behind live music (C2), the ended game returning after a restart (C4) and the reset that leaves music out (C5).

**C1. Every tablet keeps its own copy of each game fact and updates it by its own rule, on whichever events someone remembered to wire.** At a show a GM deletes a transaction and every tablet keeps refusing the token as "already scanned"; a reload does not help; a tablet that was offline during Reset All Scores comes back with the old claims. The design lets this happen because the backend decides a claim but each tablet holds a list of its own that only grows (union on reconnect, add on scan, unmark on one error), and the backend's own broadcasts leave out facts that changed by another path, such as another team's bonus moved by a delete or a team created by a scan. Behind it: blue's fix W1 (three more places that update the claimed list) and 20 findings, among them A-05 / C-04 (deleted token refused), A-06 / C-30 (reset while disconnected), B-13 (a delete sends one team's score). Questions 1 and 8.

**C2. A service's health and its own state are two facts on two delivery paths.** If Home Assistant or MPD is down when the engine starts, the lighting and music panels stay disabled all night; if MPD dies mid-show the progress bar keeps moving. The backend pushes only the health row when health changes and pushes a service's own state only on that service's events, so a panel learns of an outage only where a hand-written list happens to re-send its state. Behind it: blue's fixes W4 and W6 and 11 findings: A-11 (lighting), A-12 / B-33 (music), A-17 / B-56 (a volume change reaches no other tablet), B-34 (music's private connected flag). Questions 2 and 9.

**C3. The engine's picture of each outside program is a cache fed by a text or event stream, never re-read and carrying no age, and the video queue, the cue timelines and ducking trust it.** Blue's worst live incident, the video that stayed "stopped" for about 28 seconds, came from a parser that held each message until the next one arrived (A-68); a false "video finished" can fire two seconds in (A-61); music stays ducked after the queue is cleared (B-45); a cue with a 2-second video never completes (A-48). Behind it: blue's fixes W9 P0.1, W10 P1 and W10 F3, and 25 findings. Question 3, with 5 for the gates that read the cache.

**C4. ### C1. Every tablet keeps its own copy of each game fact and updates it by its own rule, on whichever events someone remembered to wire

**Place 1 of 16.** A valid token refused all night is the fault a GM meets most directly, and it is blue's W1, the pass's founding example (program document section 6).

**Statement.** The backend decides which tokens are claimed, which teams exist and what each team's score is. Every GM tablet, and the wall scoreboard, holds its own copy of those facts and brings it up to date through a separate handler for each message it was taught: a delete removes the transaction but not the claim, a reset while the tablet is away never reaches it, a reconnect adds to the claimed list but never removes from it, and the backend itself broadcasts a change only on the events someone wired (a delete carries one team's row; a team created by a scan sends no team event). A copy kept this way is correct only if every path that can change the fact also reaches the copy, and several do not.

**Candidate design choices (candidate, not decided).**
- (a) One versioned pack view handed to every consumer; a swap is a new view plus one "pack changed" event (backend B-c8 (A)); the engine serves only bytes that match its frozen inventory (a copy in a read-only activation folder) and sends a `pack` field with every snapshot; each client compares its loaded hash and shows "behind" (clients D-c3 (a)).
- (b) Restart-only packs: serve the file endpoints from the frozen bytes and keep manifest, tokens and files one atomic set (backend B-c8 (B)).
- (c) Clients stop holding pack files: each fetches the active pack from the engine on every start and treats its copy as disposable; the nested submodule files are removed (clients D-c3 (b)).
- (d) Each editable file gets a declared apply rule (live, reset, restart) in one table that both the tool and the README read, and the tool shows "pending until X" (clients D-c11 (a)); or a single apply verb on the engine (hot-apply) re-activates the pack, re-reads the files and returns the new identity (clients D-c11 (b)).
