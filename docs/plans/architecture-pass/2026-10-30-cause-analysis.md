## 1. The causes in short

Sixteen causes, ordered by how much each affects a show night, most first. The first four hold the four reproductions the program document names for the rig (section 4.1, step 2): the deleted token still refused (C1), the music panel behind live music (C2), the ended game returning after a restart (C4) and the reset that leaves music out (C5).

**C1. Every tablet keeps its own copy of each game fact and updates it by its own rule, on whichever events someone remembered to wire.** At a show a GM deletes a transaction and every tablet that stays connected keeps refusing the token as "already scanned" (a reload happens to cure it, by the same path that wipes the tablet's offline scans, C4's C-05); a tablet that lost its connection during Reset All Scores keeps the old claims when it reconnects. The design lets this happen because the backend decides a claim but each tablet holds a list of its own that only grows (union on reconnect, add on scan, unmark on one error), and the backend's own broadcasts leave out facts that changed by another path, such as a team created by a scan, or every other team's row after a delete. Behind it: blue's fix W1 (three more places that update the claimed list) and 19 findings, among them A-05 / C-04 (deleted token refused), A-06 / C-30 (reset while disconnected), B-13 (a delete sends one team's score, a latent fault today). Questions 1 and 8.

**C2. A service's health and its own state are two facts on two delivery paths, and the state travels only on a hand-written list of that service's events.** If Home Assistant or MPD is down when the engine starts, the lighting and music panels stay disabled all night; if MPD dies mid-show the progress bar keeps moving. Behind it: blue's fixes W4 and W6 and 6 findings: A-11 (lighting), A-12 / B-33 / C-43 (music), A-17 (a volume change reaches no other tablet), A-102 (the hand-listed pushes). Questions 2 and 9. ### C1. Every tablet keeps its own copy of each game fact and updates it by its own rule, on whichever events someone remembered to wire

**Place 1 of 16.** A valid token refused all night is the fault a GM meets most directly, and it is blue's W1, the pass's founding example (program document section 6).

**Statement.** The backend decides which tokens are claimed, which teams exist and what each team's score is. Every GM tablet, and the wall scoreboard, holds its own copy of those facts and brings it up to date through a separate handler for each message it was taught: a delete removes the transaction but not the claim, a reset while the tablet is away never reaches it, a reconnect adds to the claimed list but never removes from it, and the backend itself broadcasts a change only on the events someone wired (a delete carries one team's row; a team created by a scan sends no team event). A copy kept this way is correct only if every path that can change the fact also reaches the copy, and several do not.

**Candidate design choices (candidate, not decided).**
- (a) The tablet shows the backend's claim list plus only its own offline scans the backend has not yet confirmed; every message that changes a fact replaces that fact's copy through one function (blue A-c1 (a); GM C-c1 (1); program document section 6).
- (b) Each fact carries a version number; a tablet that sees a version it did not expect asks for the whole fact (blue A-c1 (b)).
- (c) The tablet holds no claim list: the gate asks the backend each time the connection is up and keeps a short offline list only while disconnected (GM C-c1 (2)).
- (d) One write rule for every copy: replace by a full record carrying a version or time; or two rules only, replace for backend-owned facts and "pending local action" for the tablet's own unconfirmed scans (GM C-c2 (1) and (2)).
- (e) The backend's push layer subscribes to "this domain's snapshot changed" (a version counter per domain) instead of per-event lists, so no fact depends on a list being complete (backend B-c2 (B)).

**Candidate proving tests.** Delete a transaction on one tablet; rescan its token on a second tablet with no reload: accepted (fails today); reload the second tablet: still accepted (passes today, by the reload path above, so only the first half proves the rule) (A-05 / C-04). Drop a tablet's connection without reloading it, reset all scores from another, reconnect the first, rescan an old token: accepted (A-06 / C-30). After a delete, every tablet receives every team's row in the delete message (B-13; no delete changes another team's bonus under today's rules, so the test asserts the message itself). Submit a scan the backend answers with a general error: the token is not left locked and the GM sees why (C-31). ### C7. A reply does not say which request it answers, whether it is final, or whether the fact was stored, so each client reads replies by its own rule

**Place 7 of 16.** This is where scans are lost or replayed forever: a player's scan can vanish without anyone being told, and a GM's command can report the wrong outcome.

### C8. The engine assumes it owns the machine, and the tests assume they may use it

**Place 8 of 16.** It only bites when a test or a second engine runs on the show box, but when it does it kills the live video player; blue lived it on 2026-09-15 and it is the seam the preview engine will need.

**Statement.** The engine finds, owns and ends its helper programs (VLC, MPD, the D-Bus and PipeWire monitors, the kiosk browser) by fixed file names under `/tmp` and by command-line patterns over the whole machine, because it was written to be the only engine on the box. ### C12. The pack and the other files the config tool edits are read at scattered moments, the engine serves disk bytes under a frozen inventory, and no message says the pack changed

**Place 12 of 16.** On a show night the pack does not change, so this bites only when someone edits and does not restart; it ranks here because it is the ground hot-apply and the design loop stand on, and because a half-applied pack silently changes what scores mean.

**Statement.** The engine adopts one pack at boot and freezes its rules, but its file endpoints serve whatever bytes are on disk, its token endpoint re-reads the file on every call, and the web player scanner reads a nested copy of its own; the TV, the ESP32, the GM tablet and the config tool each load the pack at their own moment (page load, boot, first fetch, app start) and keep it.
