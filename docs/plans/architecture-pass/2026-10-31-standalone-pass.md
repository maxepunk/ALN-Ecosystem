## 1. In short

A whole standalone game has one authority for the game and none for anything else. The GM tablet decides claims, scores, teams, the phase and every boundary, from hand-kept second copies of the backend's rules; nothing under `ALNScanner/src` imports `backend/src/gameRules/` (the four mentions are comments: `src/core/modeSemantics.js:8`, `src/core/storage/LocalStorage.js:368`, `src/ui/renderers/dormancyWording.js:4`, `src/utils/formatCurrency.js:5`). The player devices decide only whether a token is known and, on the phone, whether it was seen before; they hold no shared game fact, and no channel joins them to the tablet. No record of what players found reaches anyone: the phone keeps only a seen set, and the ESP32 keeps up to 100 queue lines on its card, readable only by serial command. No video plays, no evidence is shown in public, and the pack's game clock has no reader (`2026-10-31-standalone-gm.md` section 1.3; `2026-10-31-standalone-players.md` conclusion 4).

Of the sixteen causes, four produce no fault in a standalone game because they are about the engine's own machinery (C2, C3, C8, C13), four apply in part (C1, C5, C6, C7), and eight apply in full (C4, C9, C10, C11, C12, C14, C15, C16). The first candidate design survives unchanged for five causes (C2, C3, C8, C11, C13). For the other eleven it holds only in part. Eight of them assume the engine as the sender of a message, the holder of a record or the thing being assembled (C1, C4, C5, C6, C7, C10, C12, C15), and each needs a one-sentence change so that the tablet, or each device for its own private facts, takes that place. Three fall short for reasons that remain with no engine: C9 (no shared rules module exists), C14 (the check misses the shapes two producers build and the pack-to-device file shape), C16 (rules copied across two code bases, and the ESP32's boot path, are out of reach). No candidate fails outright on every device.

The two biggest gaps. First, nothing anywhere says that a game is standalone: the tablet's deployment mode is each tablet's own tap on the first screen (`ALNScanner/src/app/sessionModeManager.js:30-40,95-110`), the phone's is its URL path (`aln-memory-scanner/js/orchestratorIntegration.js:33-34`), the ESP32 has no such notion and treats a missing engine as an outage that never ends (`arduino-cyd-player-scanner/ALNScanner_v5/services/OrchestratorService.h:1289-1313`), and the pack has no field for it (`ALN-TokenData/game.json` top-level keys). So no record says which of the pack's declared effects an engine-less game drops, and nothing can refuse mixing. Both sheets propose this as a seventeenth cause, N1, put to the owner as a question in section 3. Second, every device draws the missing engine as a failure: "Offline" on the phone all night, red "DISCONNECTED" and a rising queue count on the ESP32, "VIDEO UNAVAILABLE, Rescan later" for a video that can never play (SP-03, SP-20, SP-07), and the tablet has no readiness verdict at all (SG-09).

## 2. The sixteen causes against a whole standalone game

Each entry gives: **applies** (yes, partly or no, with one reason and a citation); **authority** (which device decides the fact this cause is about when no engine is present); **candidate** (does the analysis's first candidate design still work with no engine: yes, partly or no); **change** (the smallest change that would serve standalone too, candidate, not decided); and **card line** (the sentence for the owner's card, at most 45 plain words).

### C1. Every tablet keeps its own copy of each game fact

- **Applies: partly.** There is no second tablet to drift from, and the player devices share no game fact (`aln-memory-scanner/js/app.js:195-215`, a private seen set), but the one tablet still keeps its claim list beside its transaction list and refreshes screens only on the events someone wired (`ALNScanner/src/core/storage/LocalStorage.js:97-107,320-326`; no event on a new game, `:163-177`). Two standalone tablets are two separate games (SG-06).
- **Authority:** the one GM tablet (`LocalStorage.sessionData`, `LocalStorage.js:31-37`) decides claims, scores and teams. A second standalone tablet is a second authority. Player devices decide nothing shared.
- **Candidate (a) still works: partly.** Its first half, "the tablet shows the backend's claim list plus its own unconfirmed scans", is empty with no backend; its second half, one function replaces a fact's copy, still holds inside the tablet with the tablet's own transaction list as source.
- **Change (candidate, not decided):** the tablet derives claims, scores and group state from its transaction list through one rebuild function, the same rule the backend's `computeTeamScores` uses (`backend/src/gameRules/scoring.js:220`); the owner states whether a standalone game means one GM tablet.
- **Card line:** In a standalone game: one GM tablet holds the only copy, so tablets cannot drift, but it keeps a claim list beside its transactions and refreshes screens only on wired events. Two standalone tablets are two separate games; one tablet per game is undecided.

### C2. Service health and service state on two paths

- **Applies: no.** No venue service exists in a standalone game. The tablet's service panels carry `data-requires="networked"` and are hidden (`ALNScanner/index.html:346,366,429,476,504,517`; `ALNScanner/src/styles/screens/admin.css:10`); the phone's header and the ESP32's status screen show only a connection word (`aln-memory-scanner/index.html:23-27`; `arduino-cyd-player-scanner/ALNScanner_v5/ui/screens/StatusScreen.h:153-192`).
- **Authority:** none; there is no service to decide.
- **Candidate (a) still works: yes.** One record per service is engine-side; standalone neither runs it nor conflicts with it.
- **Change:** none.
- **Card line:** In a standalone game: no venue service runs, so this cause produces no fault. The service panels are hidden on the tablet and the player devices hold no service state. The candidate design needs no change.

### C3. The engine's picture of each outside program

- **Applies: no.** No outside program is driven. The phone plays audio itself and the ESP32 plays through its own I2S (`aln-memory-scanner/js/tokenDisplay.js:93-113`; `arduino-cyd-player-scanner/ALNScanner_v5/ui/screens/TokenDisplayScreen.h:153-166`); the tablet drives nothing.
- **Authority:** none. Video, music and lights do not exist without the engine.
- **Candidate (a) still works: yes.** One reader per program is inside the engine; nothing in standalone touches it.
- **Change:** none.
- **Card line:** In a standalone game: no outside program is driven; the tablet plays nothing and each player device plays its own audio. No fault here, and the candidate design needs no change.

### C4. No fact declares what a boundary does to it

- **Applies: yes.** On the tablet, start, pause, end, new game, reload, a change of day and a pack change each run their own code and nothing states what each does to each fact (`LocalStorage.js:75-86,163-249,300-307`; SG-01, SG-02, SG-03, SG-04, C-41). On the player devices, the phone's seen set and the ESP32's queue and token list outlive every game (`aln-memory-scanner/js/app.js:195-215`; `OrchestratorService.h:445-458`; SP-18, D-10).
- **Authority:** the GM tablet decides the phase and every boundary. No channel carries a boundary to a player device, so today each device decides its own facts' lifetime, and nothing ever triggers one.
- **Candidate (a) still works: partly.** The `{authority, lifetime}` table works if the standalone tablet is a column of it; "one boundary message to every client" has no sender with no engine, and the tablet has no channel to the player devices.
- **Change (candidate, not decided):** the boundary table names the standalone tablet as the authority and its boundaries as local calls (start, pause, end, new game, reload, day change, pack change, device replaced); each device-private fact on a phone or ESP32 gets a lifetime tied to a device action (a "new game" control on the device) or to a game id the tablet shows and the device checks. The table stays; the message is replaced by that action.
- **Card line:** In a standalone game: the GM tablet decides every boundary, but start, pause, end, reset, reload, a day change and a pack change each run their own code; the phone's seen list and the ESP32's queue outlive every game. The table needs a tablet column.

### C5. Start and Reset are two hand-kept sequences

- **Applies: partly.** There is no engine to assemble, and the player devices each have one boot path (`arduino-cyd-player-scanner/ALNScanner_v5/Application.h:1570-1656`; the phone one page load). The same shape exists in small on the tablet: a new game and Reset All Scores clear different things and raise different events (`LocalStorage.js:163-177` against `:262-293`), while fresh start and reload already share one restore function (`ALNScanner/src/app/app.js:455-495`).
- **Authority:** the GM tablet.
- **Candidate (a) still works: partly.** One `assembleEngine()` for boot and reset has no engine to apply to; the idea, one sequence for both, fits the tablet.
- **Change (candidate, not decided):** one "begin game" function on the tablet that both new game and Reset All Scores call, clearing the same facts and raising the same events.
- **Card line:** In a standalone game: there is no engine to assemble. The same shape appears in small on the tablet: a new game and Reset All Scores clear different things and raise different events. One begin-game function for both would serve.

### C6. Snapshot and live message built by different code

- **Applies: partly.** There is no snapshot and live pair, and the player devices receive neither. On the tablet the saved record is the one snapshot, and reading it back fires none of the live events, so the History badge stays hidden after a reload (A-22: `ALNScanner/src/app/initializationSteps.js:77-79`; `ALNScanner/src/ui/uiManager.js:322-326`; `app.js:455-495`).
- **Authority:** the GM tablet's saved `standaloneSession` record (`LocalStorage.js:113-115`).
- **Candidate (a) still works: partly.** One builder serving both snapshot and push fits as one apply-record function used by load and by live changes; the engine-side `describe()` has nothing to describe.
- **Change (candidate, not decided):** loading the saved game goes through the same function and raises the same events as a live change.
- **Card line:** In a standalone game: there is no snapshot and live pair. The saved game is the one snapshot; reading it back fires no live event, so the History badge stays hidden after a reload. Loading should use the same apply function as a live change.

### C7. A reply does not say which request, whether final, whether stored

- **Applies: partly.** No network reply exists. On the tablet the local store's return value is the reply and the caller ignores it: a refused scan still paints "Transaction Complete!" and marks the token (`ALNScanner/src/app/domains/gameOps.js:358-362`; `uiManager.js:466`), and refused duplicates and unknown tokens are recorded nowhere (B-08). On the ESP32 a queued scan shows the same screen as a recorded one (`Application.h:579-597`; D-17); the phone's standalone branch would claim `logged:true` when nothing is stored (`orchestratorIntegration.js:92-95`; latent, SP-22).
- **Authority:** the device that took the scan, because only it can know whether anything was stored: the tablet for GM scans, each player device for its own record.
- **Candidate (a) still works: partly.** The "persist then publish through one `commit(fact)` that returns after the save and carries failure to the caller" half fits every device as a local call. The request id and "final" flag assume a server that answers each request; nothing pairs with them locally.
- **Change (candidate, not decided):** each device's local record step returns the same result words the engine would (stored, rejected with a reason, retry), and the scan path reads that verdict before painting a result. If the owner says yes to question 19 (record every scan attempt's outcome, still open), the tablet also records refused attempts as its standalone counterpart. This is the analysis's candidate (b) for C7 applied locally.
- **Card line:** In a standalone game: no network reply exists, but each device's own store answers and the caller ignores it: a refused scan still shows Transaction Complete, and the ESP32 shows a queued scan as recorded. Each device's record step must return the same result words.

### C8. The engine assumes it owns the machine

- **Applies: no.** The tablet runs in a browser tab and starts no helper program; nothing on a phone or the ESP32 shares a machine that way. (The GM scanner's Playwright config reusing port 8443, D-61, concerns tests only.)
- **Authority:** none.
- **Candidate (a) still works: yes.** A run directory and name prefix per engine instance is engine-side.
- **Change:** none.
- **Card line:** In a standalone game: no engine runs on any machine. The tablet is a browser tab and the player devices start no helper programs. No fault here, and the candidate design needs no change.

### C9. The tablet and the player devices decide facts the engine is the authority for

- **Applies: yes.** This is the "alone in standalone" half of the cause. Every rule on the tablet is a second copy (`2026-10-31-standalone-gm.md` section 1.1, eleven rows), with holes: no scan gate outside the networked branch (`gameOps.js:233-241`; `LocalStorage.js:300-307` checks only `paused`), no transaction id (A-36), no report (A-37), a duplicate refusal that never names the team (A-34). Each player device alone decides whether a token is known, by two different matching rules: the phone lowercases and strips to `[a-z0-9_]` (`aln-memory-scanner/js/scannerCore.js:28-44`), the ESP32 matches the raw text exactly (`arduino-cyd-player-scanner/ALNScanner_v5/services/TokenService.h:160-167`; SP-16).
- **Authority:** the GM tablet decides every rule fact: claims, scores, groups, duplicates, the scan gate. Each player device decides known or unknown; the phone also decides seen.
- **Candidate (a) still works: partly.** "Standalone is the one place the tablet decides, from a shared rules module the backend also loads" is the right shape, but no sharing exists (no import of `gameRules` under `ALNScanner/src`); `gameRules` lacks three rule pieces the tablet needs: the active-game scan gate (`backend/src/services/transactionService.js:155-163`), the GM adjustment and its floor (`:113-130`), and the adjustment replay and floor of the delete-and-rebuild (`:817-894`; the recompute itself is `gameRules/scoring.js:220`); SG-11. The player rules sit in JavaScript on the phone and C++ on the ESP32, which cannot load the backend's module.
- **Change (candidate, not decided):** the shared module also holds the scan gate, the adjustment and its floor, and the adjustment replay and floor of the rebuild, in a form both the backend and the browser load; the player-side rules are shared as data, not code: one list of test cases for id normalisation and lookup, run against both player devices, so the ESP32 adopts the phone's normalisation.
- **Card line:** In a standalone game: the GM tablet alone judges claims, scores and the scan gate, from hand-kept copies of every rule, and each player device alone decides whether a token is known, by two different matching rules. No shared rules module exists yet.

### C10. No fact carries whether it is known, unknown, stale or partial

- **Applies: yes,** the widest on the player devices. A standalone game is drawn as an outage: the phone's header reads "Offline" all night (`aln-memory-scanner/index.html:23-27`; `js/app.js:595-603`; SP-03), the ESP32's status screen reads red "DISCONNECTED", "OFFLINE" and a rising queue count (`StatusScreen.h:153-192`; SP-20), a video token says "VIDEO UNAVAILABLE, Rescan later" though rescanning can never work (`Application.h:586-593`; SP-07). Failures read as normal values (SP-08, SP-09, SP-12, SP-19, D-11) and "no token database" reads as "bad tag" (SP-13). On the tablet the "plausible but wrong value" kind appears: Team Details shows a $0 bonus, Game Activity shows "Unknown, $0", an ended game draws "Active" (`ALNScanner/src/ui/renderers/GameOpsRenderer.js:221`; `ALNScanner/src/core/gameActivityBuilder.js:55-64`; `ALNScanner/src/ui/renderers/GameAdminRenderer.js:76-95`), and no readiness verdict exists (SG-09).
- **Authority:** each device for what it knows about its own copies: the tablet for the game and the pack it adopted (published at its Pages origin); the phone for its seen set and its token file; the ESP32 for its token list, its clock and its queue.
- **Candidate (a) still works: partly.** "Every pushed fact carries the time observed and known, unknown or stale" has nothing pushed in standalone, and the heartbeat alternative needs an engine. The "draw unknown differently from a normal value" half fits every device.
- **Change (candidate, not decided):** each device stamps its own copies (pack source and load time, the saved game's pack stamp, queue age) and draws "standalone by choice" and "no token database" differently from "engine down" and "unknown token"; the tablet adds a readiness line (app cached, pack current, storage working).
- **Card line:** In a standalone game: every device draws the missing engine as an outage: the phone says Offline all night, the ESP32 shows red Disconnected and a rising queue, a video token says Rescan later. Nothing says standalone by choice, and no tablet readiness verdict exists.

### C11. One question has several answerers

- **Applies: yes.** On the tablet, group completion has two answers that disagree: the list LocalStorage builds (`LocalStorage.js:394-438`, stored at `:434`) and `getTeamCompletedGroups` (`ALNScanner/src/core/unifiedDataManager.js:569-575`), which LocalStorage does not implement, so it hands an empty list to both Team Details builders (`:582-675`, `:685-741`). Claims have two places (the Set and the transactions), teams have three (C-24) and "may I scan" has none (`gameOps.js:233-241`). On the phone, "am I standalone" is one URL test written three times (`orchestratorIntegration.js:33-34`; `scannerCore.js:51-54`; `config.html:423`; SP-01) and the config page tests a connection the page will never use (SP-04).
- **Authority:** the GM tablet for every game question; each device's own setting for "which deployment mode am I in", which today is the tablet's tap, the phone's URL and nothing on the ESP32.
- **Candidate (a) still works: yes.** One resolver per question, one authoritative record every screen reads, fits with no engine: the tablet's transaction list and game record are that record, and the "labelled pending" clause is not needed.
- **Change:** none required. The players sheet adds one optional resolver (candidate, not decided): "deployment mode" becomes a question every screen asks, with the game's declared mode as its input instead of the URL.
- **Card line:** In a standalone game: the tablet answers group completion in two places that disagree, teams in three and may-I-scan in none; the phone decides am-I-standalone by one URL test written three times. One resolver per question still fits; deployment mode should become one.

### C12. The pack is read at scattered moments; no message says it changed

- **Applies: yes.** The tablet reads the pack once at app start (`ALNScanner/src/core/packLoader.js:23-26`), compares nothing afterwards and stamps nothing on the game (`LocalStorage.js:31-37,164-172`). Of the engine's gate checks it applies only the exact schema-version match (`ALNScanner/src/core/tokenManager.js:60-66`), plus two warnings (`tokenManager.js:126-140`; `ALNScanner/src/core/modeSemantics.js:119-133`); it reads neither `requires` nor `engine.minVersion` (`backend/src/services/packService.js:728-735,762-767` have no counterpart under `ALNScanner/src`). A reload while online mid-game adopts the newest published pack under the old game (SG-03, SG-08, B-29). The phone serves its own nested copy, pinned at `15d8d2e` while `ALN-TokenData` is at `6f9bc30`, with no `game.json` and no `pack-manifest.json` (`ls aln-memory-scanner/data`; D-05 / A-94, SP-10); the ESP32 serves whatever its card last held and reports no identity (`AssetService.h:148-158,229-231`; D-06).
- **Authority:** for the tablet, the published pack at the Pages origin decides the rules and the tablet decides when to adopt it (app start). For each player device, the pack copy loaded onto it. Nobody decides the game's pack.
- **Candidate (a) still works: partly.** The engine's versioned view, the `pack` field in every snapshot and the "pack changed" event have no sender. The tablet has a comparison point, the manifest it fetches at start; the player devices have none.
- **Change (candidate, not decided):** the game record on the tablet carries the pack hash it started under; the tablet checks the published manifest only between games, shows "behind", and never swaps mid-game. Each player device stamps the pack's content hash when its copy is loaded and shows it on every screen that can; the tablet's hash is the one the others are checked against by eye.
- **Card line:** In a standalone game: each device loads whatever pack copy its source holds; the tablet can adopt a newer pack on a mid-game reload, and the game carries no pack stamp. No player device shows a pack identity, so nothing compares the devices.

### C13. The engine does not know who is connected

- **Applies: no.** No engine, no credential, no socket and no registry exist. Each device is its own identity (`orchestratorIntegration.js:20-29`; the ESP32's `DEVICE_ID`). The tablet's device id stays `001`, set only by the networked wizard (`ALNScanner/src/ui/settings.js:19,35`; `ALNScanner/src/ui/connectionWizard.js:388`), a consequence recorded under C1 (SG-06).
- **Authority:** nobody; each device is known to nothing but itself.
- **Candidate (a) still works: yes.** An audience declared with each event and route is engine-side.
- **Change:** none.
- **Card line:** In a standalone game: no engine, no credential and no connection exist, so this cause produces no fault. A tablet never set up for a networked game keeps device id 001 and is known to nobody (see C1). The candidate design needs no change.

### C14. Joins kept by hand, nothing checks the sides agree

- **Applies: yes.** On the tablet both sides of each join sit on one device and still disagree: Team Details reads `backendScores` and `getTeamCompletedGroups`, which standalone never fills (A-03 / A-04 / C-06); Game Activity reads the lookup's wrapper (A-07); the tablet's transaction lacks `id`, `status`, `summary` and `owner` that readers expect (SG-12); the pack's `requires` is read by no one (SG-08). Between pack and player devices: the pack's token file is flat and the ESP32 reads only a top-level `tokens` object (`TokenService.h:125-129`; the wrapper exists only in `backend/src/routes/resourceRoutes.js:57-61`; SP-14); the audio extension rule differs (SP-15); the phone never reads `processingImage` (SP-06).
- **Authority:** the GM tablet for the tablet's own joins; the pack's schema files (`ALN-TokenData/tokens.schema.json`) decide the shapes, and each device parses by hand.
- **Candidate (a) still works: partly.** A start-up and test-time check that every element id, listened event and subscribed message has one definition runs in the browser alone, but it covers neither the shape of a transaction two producers build (the backend and the tablet) nor the file shape between pack and device.
- **Change (candidate, not decided):** one transaction shape, written once and checked against both producers; the pack's `requires` list checked at load on the tablet; a check that loads the real pack token file through each player device's reading rules (the flat file, the wrapper, the audio extensions) and fails on a mismatch.
- **Card line:** In a standalone game: both sides of each join sit on one device and still disagree: Team Details reads scores standalone never fills, the ESP32 wants a wrapped token file the pack lacks, the phone ignores processingImage. One shape per join, checked against every producer.

### C15. Several separately versioned checkouts and hand-run steps

- **Applies: yes.** A standalone game's whole supply chain is this cause. For the tablet: the Pages build runs on every push to the scanner's `main` (`ALNScanner/.github/workflows/sync.yml:3-7,37-48`), so the hand step is moving the scanner's `data` pin, which fixes the pack the Pages tree serves (`ALNScanner/vite.config.js:25`); a service-worker cache with no precache (`ALNScanner/sw.js:3-7`); no build id on screen (SG-09). For the phone: a hand-run `sync.py --deploy` or manual workflow publishes the page to GitHub Pages (`aln-memory-scanner/.github/workflows/sync.yml:3-4,26`), and the QR library comes from `unpkg.com` (`aln-memory-scanner/index.html:138`; `sw.js:27-30`; SP-21, D-19). For the ESP32: a fresh card holds one file and only the engine's sync fills it (`arduino-cyd-player-scanner/sd-card-deploy/assets/images/`; `TokenService.h:203-264`; SP-13).
- **Authority:** the person who publishes or copies: the Pages publish decides the app shell and pack for tablets and phones, the card copy for each ESP32. Nothing checks the result.
- **Candidate (a) still works: partly.** The boot check comparing pack hash, scanner build id and submodule pins assumes the engine reports identity at boot; the one deploy command fits as is.

### 3.4 The proposed new cause, N1, as a question for the owner

Both sheets, reading different devices, arrived at the same proposal and named it N1. In one sentence: **nobody declares that a game is standalone, so no record says which of the pack's declared effects an engine-less game drops, and nothing can refuse mixing.** Its eight instances: SG-05, SG-07, SG-10 on the tablet; SP-02, SP-05, SP-06, SP-11, SP-17 on the player devices.

Why the sheets say it is new, not one of the sixteen. C11 holds the phone's three URL tests (SP-01) but not the missing declaration itself. C10 holds the screens that misread a standalone game as an outage but not the reason they have nothing better to read. C13 is about credentials and station names. C14 is about names and shapes kept by hand on two sides; a property of the whole game that no record holds anywhere is not a two-sided join. The ESP32's missing standalone mode is not N1's reason: decision 22 settles that as parity, and section 4 is the parity list.

Where each instance would go if the owner says no. SG-05 and SP-02 (no declaration, nothing refuses mixing): C11, as "which deployment mode is this game" answered by each device's own tap, URL or nothing. SG-07, SG-10 and SP-06 (the pack declares a surface, a clock, a video; the device has no reader): C14, as a pack-to-device join nothing checks. SP-05 (nothing records player discoveries): C9, as a fact with no standalone authority. SP-11 and SP-17 (the ESP32 cannot be configured without an engine, and starts slowly): the parity table (rows 1, 2, 18, 23), with SP-17's outage-reading half under C10.

The nearest existing idea, from the players sheet (candidate, not decided): the engine already says a service can be **dormant** with a stated door, "not installed tonight" (CONTEXT.md section 4, "Dormant vs fault", line 344, and section 5, lines 418-426; root `CLAUDE.md`, `dormancyService`). (3) What does exposure do with no TV, and what does a video token do with no engine (SG-07, SP-06, SP-07)? (4) Is "standalone" a property of the game record, the pack, the profile, or each device?

## 5. What this means for the rule design (step 3)

- **Every rule names its authority with the engine absent.** Eight of the sixteen first candidates assume the engine sends a message, holds a record or is the thing assembled (C1, C4, C5, C6, C7, C10, C12, C15). Each rule must say who takes that place in a standalone game: the GM tablet for every game fact (claims, scores, teams, phase, boundaries, the pack stamp), and each player device for its own private facts (known tokens, seen set, queue, pack copy). A rule that only works when the engine is present fails decision 22.
- **"Standalone" must be a declared fact somewhere, and the rules must say where.** Today it is a tap, a URL or nothing (SG-05, SP-01, SP-02). Until the owner answers N1's questions, the boundary rule (C4), the resolver rule (C11) and the staleness rule (C10) each have an undefined input. The dormancy idea (a profile with no engine equipment, so every engine duty reads as "not installed tonight") is the one candidate in the tree that already carries the right words.
- **The parity surface must grow or the sharing fails.** The shared rules module C9 proposes must hold the scan gate, the adjustment and its floor, and the adjustment replay and floor of the delete-and-rebuild as well as `gameRules` (SG-11), in a form a browser loads; the player-side rules (id normalisation, lookup, audio extension) can only be shared as data run against JavaScript and C++ alike (SP-14, SP-15, SP-16).
- **The pack reaches standalone devices by hand, so the pack rule needs a per-device stamp and a between-games check.** With no engine to compare against, each device must show its pack hash and the game record must carry the hash it started under; a mid-game swap must be refused on the tablet (SG-03) and visible on every device (SP-10, D-05, D-06).
- **The test rule needs cross-implementation and real-folder proofs.** Extend the one existing cross-mode proof (backend E2E `07c`, scoring only, group case skipped on the shipped pack) to every rule family, or run the same transactions through the backend's `gameRules` and the tablet's `LocalStorage` in a unit test; one proof per player device against the deployed folder with no network; a native test of the ESP32's boot decision with no engine. The ESP32's standalone mode itself is a parity item (section 4), and it starts from a device that already scans with no engine (SP-11).
