# The runtime-state map: one table for the whole engine

Merge of the four reader sheets of the architecture pass (`2026-10-30-map-backend-game.md`, `-backend-show.md`, `-gm-scanner.md`, `-clients-tests.md`), read in full on 2026-10-30 against branch `claude/nice-curie-hescfv` at `26fc2f2` (the sheets confirmed the code they read matches that commit). Terms follow `CONTEXT.md` §2, §4 and §4b: a **runtime fact** is something a running game changes; its **authority** is the one place that decides it (an engine module, or an outside program such as VLC); a **copy** is the same fact held anywhere else; a **delivery path** is how the fact reaches a screen. "Live" below means the client is told when the fact changes; "snapshot" means it learns only on connect, on request, or on reconnect. Nothing was run. Where two sheets disagreed I read the code; those places are marked **(checked)** and the verdict is given in the row.

Row ids `R1` to `R61` are referenced by the checklist at the end.

## 1. Conclusions

What the map shows about the engine as built, for a reader who knows the game but not the code.

1. The engine keeps almost every game fact in one object: the current game session (teams, scores, transactions, claimed tokens, player scans, devices). That part is sound. Everything the GM, the TV or a player device shows is a copy of that object or of a service's memory, and the engine has no rule for how a copy must behave. Each client invented its own. The GM scanner alone uses four different rules for its copies: replace (transactions, service panels), merge (the session record), add-only (team scores, claimed tokens, device list) and "keep unless told otherwise" (the claimed-token set).
2. No copy anywhere carries an age or a stale mark. When the socket drops, the GM scanner and the TV keep showing the last numbers, the TV's countdown keeps ticking, and the GM's admin dot is not redrawn. When the orchestrator restarts, its own pictures of VLC and MPD start empty or default until the next signal arrives, while VLC and MPD may still be playing.
3. The same fact reaches a screen by two differently built messages. The full snapshot (`sync:full`) and the live events are built by different code for the session record, the device list, player scans, the game clock, the cue engine and the display mode, and by duplicated code for transactions. The GM scanner then applies the snapshot with one rule and the live event with another. Two more surprises follow: the device list the GM holds alternates between "everyone ever" and "connected only" depending on which message came last, and after a system reset the snapshot that follows a scores reset carries the old transaction list, so the GM history and the TV evidence come back after being cleared (checked, §4).
4. Several facts have more than one authority today (§3): the session's status lives in three places; "is a video playing" has six readers that disagree while a video is paused; the kiosk display reports health from the kiosk process while the mode is the engine's intent; held items live in two stores; the pack is "frozen" as a parsed snapshot but served as live disk bytes, so after a config-tool publish without a restart the GM scanner, the TV, the player scanners and the engine can hold four different packs.
5. Copies that only grow are the rule, not the exception (§3): session counters that never decrement, a device list that never forgets, the GM's claimed-token set that never releases a token the GM deleted, per-session browser keys that are never removed, a GM score map and a TV score table that are never pruned, a stopped game clock whose elapsed time keeps counting.
6. Outside programs (VLC, MPD, PipeWire, BlueZ, Home Assistant, the kiosk browser) are read by parsing their text output or by listening to an event stream. When the stream dies, nothing re-reads; a 15-second probe covers six of nine services and never the display; a health change pushes only the health row, never the service's own panel, so "music connected" and "music healthy" can disagree.
7. Boundaries are uneven (§8 Q6). Game session end clears the session but not held items, running cues, the video queue, or the once-fired cue sets; a plain "new session" does not run a system reset, so a once-cue spent in one game stays spent in the next; a system reset drops music from its rebuild (production path), leaves the display health red, reaches no client with a fresh snapshot, and reverses the listener order the engine booted with; a page reload on the GM scanner wipes the offline scans it had just restored.
8. Tests and a second engine share the live machine through fixed pid files, machine-wide `pkill` calls, one MPD socket, the kiosk window and the real PipeWire and BlueZ (§7). None of blue's eight machine-sharing fixes exists in this tree.
9. The truth sweep and the pass are different work. The sweep (retired charter, `ROADMAP.md` §4 Block 3) took every copy and every path as given and asked whether each admin-panel cell drew the right value from its service-state domain; it excluded the score, transaction and session screens, which is where this map finds the worst disagreements (R4, R5, R7). The pass asks who decides each fact and how a copy may be written; its answers would remove whole classes of the sweep's cells rather than fix them one by one. The five desync bugs the sweep recorded are all instances of rows in this map.
10. What is missing, in one sentence: a rule for runtime state like the one-truth rule for readiness (`CONTEXT.md` §2), naming one authority per fact, one write rule per copy (replace, with a stale mark), one message shape per fact for live and snapshot, and a stated behaviour at each boundary.

## 4. Facts that travel on more than one path, and snapshot and live update built by different code

### 4.1 Four routes from the backend

A fact can reach a client by (a) a live event, (b) the `sync:full` snapshot, (c) an HTTP snapshot (`GET /api/state`, `/api/session`, `/health`), or (d) a file the client fetches itself (`/api/tokens`, `/api/pack/files/*`, the PWA's own `data/tokens.json`). Every fact in R1-R16 travels on at least two of them. The GM scanner then applies the same fact through three internal paths: `service:state` → `StateStore` → renderers; `messageRouters` → `UnifiedDataManager` → `NetworkedStorage`; and `MonitoringDisplay._handleMessage` listening to `message:received` directly for the session, teams, devices and display mode (`MonitoringDisplay.js:35,216-258`). The session record is consumed twice from one event with two merge rules (`messageRouters.js:197-202` merge; `MonitoringDisplay.js:223-228` replace into `SessionRenderer` and `TeamRegistry`).

## 7. Machine sharing

What a second engine, or a test run, can touch on the live machine today (clients sheet §4; nothing was run, every claim is from code).

## 8. The six questions

The questions are those of the definition session's decisions 1 and 5 (now `docs/plans/2026-10-30-architecture-pass.md`, Appendix A). Each is restated in plain words first, because two of them did not land in the owner's reading; then the evidence from this map; then what the map shows that the six questions do not ask.

**Q1. Who decides each fact the GM sees (the authority)?** In plain words: for every number or light on the GM's screen, is there exactly one place that decides it, and does the screen show that place's answer?

Evidence. Game facts have one authority in the engine, the current game session (R1-R10). The GM screen does not always show it: the result screen shows locally computed points before the backend answers (R5, `uiManager.js:473`); the team-details screen shows a local sum because its lookup reads a field that does not exist (`GameOpsRenderer.js:221`), so group bonuses and admin adjustments never appear there while the scoreboard screen shows them; the scan gate uses a local claimed-token set that the backend's own delete never releases (R7); the Game Activity view derives "claimed" from a different copy than the gate does (R8). Show facts have an authority the engine does not control (VLC, MPD, PipeWire, BlueZ, HA, the kiosk) and the GM sees the engine's copy of it, which is sometimes a default rather than a reading (R30, R37). Thirteen facts have more than one deciding place (§3.1). The pack has one authority in principle and five in practice (R15). The player scanners decide the one fact the engine would like to own, which team a scan belongs to, and decide it wrongly (R9). So the answer today is: one authority for game facts, honoured by some GM screens and not others; shared or unclear authority for show facts, the display, held items and the pack.

**Q2. Does a service's state travel with its health?** In plain words: when the GM is told that the music service (or VLC, or the lights) is up or down, does the panel that shows what that service is doing get updated in the same breath, or can one say "down" while the other still shows "playing"?

Evidence. They travel apart. A health change pushes only the `health` domain (`broadcasts.js:536-538`); no service pushes its own domain on a health change, and the only other listener of `health:changed` is the video queue's `video:recoverable` (R46). The `connected` fields inside `video`, `bluetooth` and `lighting` are read from the registry only when some other event triggers a push (R30, R41, R44); `music.connected` is a private flag that a dormant latch leaves true while the health row says dormant (R37). Health rows are pushed only when the status word changes, so message and last-checked time ride the snapshot alone. The TV drops every `service:state` domain but `gameclock` (`scoreboard.html:1792-1795`). Dormancy changes the registry and the cue engine but stops nothing (R47). So: no, the two travel on different events at different times, and the GM's four "is video available" views (health row, video panel, held list, per-cue disable) arrive as four separate pushes (§5).

**Q3. How does the engine read the programs it drives?** In plain words: the engine starts and controls other programs (VLC for video, MPD for music, PipeWire for sound routing, BlueZ for speakers, Home Assistant for lights, a browser for the TV). When the engine needs to know what one of them is doing right now, how does it find out, how sure can it be, and what happens when the program changes behind its back?

Evidence. Every one of them is read by parsing text it prints, or by listening to a stream of text events (§6). No reading carries an age; no copy is marked stale. Three programs start their copy at a default instead of a reading: the VLC copy is empty until the first signal (R30), the MPD copy says stopped/70/no track until the first idle event (R37), the kiosk's `visible` flag is whatever the last call set (R32). When an event stream dies, nothing re-reads: the `gave-up` event has no listener (R52); the 15 s probe covers six of nine services and never the display (R46); the probe fixes VLC's `state` but never its `track` or volume (R30). A stale copy is also possible with a live stream: a missed PipeWire `remove` leaves a dead sink-input index (R33); a signal from another MPRIS player can mark VLC healthy (§5). The pack and token files are read the same way, as disk bytes under a manifest frozen at boot (R15, R16). So: by text parsing and event streams, with no age, no stale mark, and no re-read on failure.

**Q4. Can anything other than the live engine touch the live show?** In plain words: tonight's game runs on one orchestrator. If someone runs the test suite on that same machine, or a second orchestrator (tomorrow's preview engine), can it change what the audience and the GM see or hear: kill the video, mute the music, open a window on the TV, pair a speaker, change scores?

Evidence (§7). Yes, in several ways, all from code: a second orchestrator reaps the first one's VLC, MPD or monitor child through the shared pid files (R52); every kiosk launch SIGKILLs any other kiosk on the machine; every audio-service start kills every `pactl subscribe` on the machine and sets every HDMI card's profile; eight contract-test files and twenty-one integration-test files reach those calls; the integration tests pre-launch the kiosk on the real display; Tier L runs three orchestrators that adopt the live display, PipeWire and BlueZ when they are present, listen on the venue LAN with a known password, and write placeholder video files into the live media directory; four flows pin the venue profile and drive the real Home Assistant and speaker; the rung-1 scripts delete the pid files and SIGTERM whatever is in them. Scores are safe: test storage is in memory under `NODE_ENV=test`. None of blue's eight fixes for this is in the tree. So: yes, through fixed files, machine-wide kills and the real display and audio stacks.

**Q5. Does one question get one answer?** In plain words: when two parts of the system ask the same question ("is a video playing?", "is this token taken?", "what is team 3's score?"), do they read the same place and get the same answer?

Evidence. No. Twenty-three questions have more than one answerer (§5). The clearest: "is a video playing" has six readers that disagree while a video is paused (§3.1); "is this token claimed" has four backend readers and four GM readers that disagree after a delete and after an offline claim by another station; "what is team X's score" has nine readers and the GM contradicts itself between two of its own screens; "is the display healthy" disagrees in four ways; "which pack is running" has six answerers after a publish. The one question with one answer, "is the system offline", has an answer nothing ever sets (R11).

**Q6. What does each fact and each copy do at a boundary?** In plain words: when a game starts or ends, when the GM runs a system reset, when the orchestrator restarts, or when a pack is published while the system runs, which facts are cleared, which are kept, and does every screen find out?

Evidence, by boundary. Game session end: the session record is nulled (R1) but held items (R26, R27), running cues (R23, left `running` with no tick), the video queue (R28), the once-fired cue sets (R24) and the clock's growing elapsed (R21) stay; the GM clears nothing and blocks scans by its status gate; the TV stops cycling. New game session: the engine ends the old one and clears game facts; the GM clears claims, transactions, player scans and scores on the id change but merges the session record and keeps the service panels, devices and the team registry (R1, R3, R13); the GM's persisted offline scans are wiped, including right after a reload (R12); a plain "new session" does not run a system reset, so spent once-cues carry over (R24). System reset: music is left out of the rebuild on the production path (R37); `display` stays red (R46); the listener order reverses so a later scores reset hands the GM and the TV the old transaction list (R4); no snapshot reaches any client at the end of the reset (GM sheet §6 step 18); the pack, profile, token catalog, batch cache and operator tokens are not rebuilt (backend-game §4.2). Restart: the session, clock and standing cues are restored from disk; running cues, queues, held items, music and VLC copies are lost or defaulted while the programs keep playing (R23, R28, R30, R37); every credential dies (R18); the ESP32 and the TV recover by their own rules (reboot sync, page reload). Pack change while running: the engine ignores it, the file endpoints serve it, the TV reads part of it, the GM rejects it until reload, the PWA never sees it, the ESP32 sees it at its next boot (R15); no event exists to tell anyone (§4.2). So: every boundary has a different list, none is written down, and no client is told to re-check after a reset.

**What the map shows that the six questions miss.**

1. *The write rule of a copy.* The questions ask who decides and how the fact travels, not how a copy may be changed when it arrives. The GM uses replace, merge, add-only and union for different copies of facts from the same message (§2, R1, R5, R7); the TV uses replace for snapshots and add for events. Most of §3.2 and the "it only grows" lesson come from this, not from authority.
2. *The shape of the message.* The snapshot and the live update of one fact are built by different code for seven facts (§4.2), and three clients then adapt the shapes differently. One message shape per fact is a decision the questions do not name.
3. *Who receives what, and whether they should.* The player scanners receive no runtime state at all and decide "does a session exist" from a scan reply (R1); the TV receives everything the GM does and drops most of it; unauthenticated sockets receive `session:update` with the full metadata and can request a full snapshot (R18). The planned seventh question covers this and the map says it must include the credential tiers.
4. *Stale marks and ages.* No copy in the engine or any client carries the time it was last confirmed (Conclusion 2). A rule for authority does not by itself give the GM a way to see that a number is old.
5. *Contract drift as a state problem.* The code and `asyncapi.yaml` disagree on three payloads (music `playlists` and `playlist`, cue-engine `loaded`, game-clock keys) and on one event (`gm:identified`) (§4.3); a copy that is built from the contract and a copy built from the code differ before any runtime failure.
6. *Dead and unreachable paths that still shape behaviour.* The backend offline queue (R11), the operator dormancy door (R48), `validateCommand`, the `HeldItemsStore` video branch, the `batch:ack` that no device receives (R12), the GM's standalone delete button (R58). They are not state defects but they make the engine's stated behaviour differ from its real one, and the pass's answers will be read against the stated one.
7. *The teams on player scans.* Player devices send a team the session never declared (R9). Whether a player scan should carry a team at all is a design question the six questions do not reach, and the Game Activity view and the report both read the field.
