The design words

Each card ends with the reason restated in the vocabulary step 3 uses.

Module
Any part with an inside and an outside, from one function to the whole backend.
Interface
Everything another part must know to use it.
Seam
Where one part meets another, and where behaviour can be swapped.
Deep, shallow
A deep module does a lot behind a small interface. A shallow one makes its callers know almost as much as it does.
Locality
A fix in one place fixes it everywhere.
Leverage
One module serving many callers.

Standalone games

Your decision 22 adds a requirement: a whole game can run with no engine, the GM tablet and the player scanners each working alone. In a standalone game the GM tablet decides everything about the game (claimed tokens, scores, teams, the game's start, pause and end) from its own hand-kept copies of the engine's rules. Each player scanner decides only whether a token is known.

Four causes produce no fault in a standalone game (C2, C3, C8, C13), four apply in part and eight in full. The candidate designs hold for five causes as they are, eight need a small change so that the tablet takes the engine's place, and three fall short (C9, C14, C16). Each card now says what its cause means in a standalone game.

The two biggest gaps. Nothing says that a game is standalone: the tablet is set by each GM's tap, the phone by its web address, and the ESP32 has no such setting. And every device shows the missing engine as a failure: "Offline" on the phone all night, red "DISCONNECTED" on the ESP32, "VIDEO UNAVAILABLE, Rescan later" for a video that can never play.

Screens keep their own versions of the game

The engine decides the game: who claimed which token, each team's score, whether a game is running. Every screen also keeps its own version of those facts and updates it by its own rules. These five causes are how the screens' versions drift from the engine's. Your decision 11 already puts the questions that cover them (1, 6, 8 and 9) into one rule for live state.

C1

Each tablet keeps its own list of claimed tokens

19 findingsQuestions 1, 8Blue fixed: W1

At a show A GM deletes a transaction. The engine frees the token, but every tablet that stays connected keeps refusing it as already scanned until someone reloads. A tablet that drops its connection during Reset All Scores comes back still holding the old claims, and refuses tokens the engine has cleared.

Why it happens The engine decides which tokens are claimed, but each tablet holds a copy that only grows: added on scan, merged on reconnect, removed only when a scan fails. The engine's own messages also skip facts changed by another path, such as a team created by a scan.

In a standalone game one GM tablet holds the only copy, so tablets cannot drift, but it keeps a claim list beside its transactions and refreshes screens only on wired events. Two standalone tablets are two separate games; one tablet per game is undecided.

In design terms The engine's transaction service should own the claimed-token fact; tablets should hold only its copy. Today the tablet's networked storage module updates its copy through one hand-wired handler per message, so the seam leaks: any path without a handler leaves the copy stale. No locality.

  • A-24 / C-29 After a reload a tablet knows only its own claims; a rescan of another station's token shows success, then rejection.
  • B-13 A delete recomputes every team's score but the message carries one team's row; latent today.
  • B-19 A scan for a team nobody added creates the team silently; no team message reaches any tablet.

C6

Reconnect snapshot and live update are built apart

11 findingsQuestions 9, 8

At a show A GM reloads a tablet mid-game. The History badge stays hidden until the next scan, and a rebuilt admin panel can show the clock as --:-- until the next change. The device list flips between everyone ever and connected only, depending on which message came last.

Why it happens For each fact the engine has one builder for the connect snapshot and another for the live message, and six places send the snapshot with hand-picked arguments. The tablet applies each by a different rule, and the restore path fires none of the events screens listen for.

In a standalone game there is no snapshot and live pair. The saved game is the one snapshot; reading it back fires no live event, so the History badge stays hidden after a reload. Loading should use the same apply function as a live change.

In design terms Each fact's engine module should own one description of itself, serving snapshot and live push alike. The snapshot builder is shallow: its interface is a hand-passed list of every module, and five tablet adapters reshape its output, so the seam leaks both ways.

  • B-31 Six places send the full snapshot and disagree on which devices to include and which extra keys to add.
  • A-32 / C-44 Snapshot and live shapes differ for clock and cues; five adapters reshape them, and the clock adapter drops unnamed fields.
  • D-01 A TV reloaded during a video shows its last overlay state, because the snapshot's display status is never read.

C7

A reply never says which request, final or stored

18 findingsQuestions 1, 8

At a show Player devices upload their queued scans while no game exists. The engine answers processed, stores nothing, and both devices delete the scans. A GM's scan that can never succeed comes back as a generic error, so the tablet replays it at every reconnect with a toast each time. A slow Reset System reports failure and the new game is skipped.

Why it happens The engine answers before or without the write that makes the fact true, calls an unstored batch processed, returns some failures as a typed result and others as a generic error, and acknowledges commands by action name alone. Each device then decides for itself what a reply means.

In a standalone game no network reply exists, but each device's own store answers and the caller ignores it: a refused scan still shows Transaction Complete, and the ESP32 shows a queued scan as recorded. Each device's record step must return the same result words.

In design terms One commit module in the engine should own each request's outcome: which request, final or not, stored or not. That interface is split between typed results, generic errors and action-name acks, so the seam leaks and three clients each keep their own reply rule.

The findings behind it, and the code they live in
  • B-64 / C-32 Scan failures like no session or queue full come back as a generic error; the tablet replays them on every snapshot.
  • B-22 / D-13 / D-14 A batch arriving with no game is answered processed but stored nowhere; both player devices delete it.
  • B-21 / D-15 A batch retried after an engine restart is stored twice; processed batches are remembered in memory for an hour.
  • B-69 / C-35 A system reset slower than the tablet's five-second wait reports failure, and the follow-on create session is skipped.
  • B-65 / C-33 A command ack carries only action, success and message, so two presses of one action resolve on the first reply.
  • D-12 One failed batch is dropped by the web scanner on any 4xx but kept forever by the ESP32.

C9

Tablets and phones decide facts the engine owns

18 findingsQuestions 1, 5

At a show A GM scans a token; the result screen says Transaction Complete with points the tablet worked out itself, before the engine has answered. The engine may refuse, and the correction arrives as a small toast. In standalone mode the tablet is the only judge, and its rules have gaps: a scan into a paused game shows complete and records nothing. A phone says revisited for last week's token.

Why it happens The engine is the authority for scoring, claims and the scan gate, but the tablet carries its own copy of those rules, kept in step by hand and by comment, and the player devices pick their own team and their own new-or-seen. Each device shows its own verdict first.

In a standalone game the GM tablet alone judges claims, scores and the scan gate, from hand-kept copies of every rule, and each player device alone decides whether a token is known, by two different matching rules. No shared rules module exists yet.

In design terms The engine's game-rules module should own scoring, group completion and duplicate rules behind one interface both sides load. Today the tablet holds a second implementation kept in step by comment, so the seam leaks verdicts: a rule change lands in two places, with no locality.

The engine's picture of the programs it drives

The engine drives VLC, MPD music, the audio system and Home Assistant lights, and shows their state on the GM panel. These two causes are how that picture goes stale or wrong.

C2

Service health and service state travel on separate paths

6 findingsQuestions 2, 9Blue fixed: W4, W6Seen live

At a show If Home Assistant or MPD is down when the engine starts, the lighting and music panels stay disabled all night. If MPD dies mid-show, the health row turns red alone while the music card keeps its playing look and the progress bar keeps moving. A volume change on one tablet's audio panel never reaches the other tablets' sliders.

Why it happens Each venue service keeps two facts: its health in a central registry and its own state in its own record. The engine pushes the health row when health changes, and pushes a service's state only on a hand-written list of that service's events. An outage is on no list.

Seen live The owner reports the GM panel falling behind live music on blue's line until a refresh.

In a standalone game no venue service runs, so this cause produces no fault. The service panels are hidden on the tablet and the player devices hold no service state. The candidate design needs no change.

In design terms Each service module should own one record carrying health and state. Today the seam leaks: the broadcast module re-implements each service's change set as a per-domain event list, so the interface callers must know is the full event list, and locality is lost.

  • A-17 A per-stream volume change on one tablet never reaches other tablets' sliders; the audio push list names no volume event.

Engine trusts its stale picture of outside programs

Moments when everything changes at once

A game starting or ending, Reset System, the engine restarting and a new pack being published each change many facts at once. Nothing in the engine says what each fact should do at those moments, so each one handles whatever its author remembered.

C4

Nothing says what a game boundary clears or keeps

22 findingsQuestion 6Blue fixed: W8

At a show The GM ends the game and restarts the engine; the ended game comes back as the current one and player scans keep landing in it. When the game ends, a tablet that reconnects loses its history and the wall scoreboard goes blank. A once-only cue spent in game one stays spent in game two.

Why it happens Game start, end, reset, engine restart, tablet reload and reconnect each have their own code in each component. No table says, per fact and copy, whether a boundary clears, keeps or re-fetches it, and no message announces a boundary; screens infer one from a changed session id.

In a standalone game the GM tablet decides every boundary, but start, pause, end, reset, reload, a day change and a pack change each run their own code; the phone's seen list and the ESP32's queue outlive every game. The table needs a tablet column.

In design terms A boundary-table module should own each fact's lifetime at a game boundary: clear, keep or re-fetch. No such interface exists, so the session, cue-engine, reset and tablet modules each encode their own cases; the seam leaks and one boundary change has no locality.

C5

Boot and Reset System wire the engine differently

7 findingsQuestion 6Seen live

C12

Pack edits reach each part of the kit differently

20 findingsQuestions 6, 5, 8

At a show A designer publishes a pack change and does not restart. The TV shows evidence by the new rules while the engine scores by the old. The file the engine serves no longer matches the hash in its own manifest, so a scanner that checks rejects it. A tablet running a different pack is only written to the log; nothing tells the GM. The publish tells the running engine nothing.

Why it happens The engine freezes one pack at start, yet its file endpoints serve whatever is on disk and its token endpoint re-reads every call. The TV, tablet and hardware scanner each load it at their own moment and keep it; the phone reads its own copy. No message says it changed.

In a standalone game each device loads whatever pack copy its source holds; the tablet can adopt a newer pack on a mid-game reload, and the game carries no pack stamp. No player device shows a pack identity, so nothing compares the devices.

In design terms The pack service should own one versioned pack view. Its interface leaks the disk: it checks a path against the frozen inventory, then serves live bytes, and the token service re-reads the file around it, so frozen and live state cross the seam. No locality.

C8

Engine and tests both assume they own the machine

41 findingsQuestion 4Blue fixed: W9 P0.3, W10 P2, W10 P3, W10 P4, W10 C1Seen live

At a show On 2026-09-15 a unit test killed the live show's video player on blue's tree. In this tree the same run kills the live engine's VLC signal monitor and overwrites its process files. A killed engine leaves a full-screen player behind. Twenty-one test suites open a browser on the show TV. The operator's health script says VLC not found while the player runs.
