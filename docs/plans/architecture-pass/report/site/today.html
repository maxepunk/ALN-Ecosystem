Today's engine

This page is evidence. It says what today's engine already does for each promise, which pieces are already well built, and where it falls short: sixteen design flaws, each a situation any new design must handle, with whether it was seen live or reproduced in a test. Every design from the panel and the design rounds is checked against these situations.

Nothing here drives the design. Blue's fixes and the findings behind each flaw are clues to where today's design is off, never the driver (Blue's fixes are evidence of design causes); the panel sees this page only after its first proposals. Under each flaw, folded, is how the earlier candidate would remove it; that candidate is one input among the panel's, not a decision.

Standalone today, with the table comparing the hardware scanner with the phone's scanner, and the evidence (the totals, the findings set aside with their reasons, and where each flaw lives in today's code) close the page.

What works today

What each promise already has

  • The designer's game is the game the whole kit playsPacks that hold tokens, modes, scoring, groups and cues; a gate that refuses a broken pack; a second, toy game kept beside ALN.
  • One game, the same on every screenOne game record on the engine; a full catch-up to each screen when it connects; live updates for scores, transactions and player scans; the TV and Pi 4 scoreboards.
  • Every tap gets its answer, and the night can be told afterwardsGM scans scored as transactions; player scans kept in the game record; an answer to every GM command; the post-game report and an after-game check that the night's records add up. Outside the engine, the director pastes that report by hand into ALN's article writer, the Director Console.
  • The room does what the designer cued and the GM askedVideo on the TV, music, sounds, lights, the Bluetooth speaker and audio routing; cues and timelines; the health dashboard; items held while a service is down.
  • Each lifecycle button does exactly what its name saysCreate, start, pause and end a game; Reset System; a game restored after an engine restart; the game clock.
  • The designer changes a value and plays it within minutes, and the live show never noticesThe config tool; a store for drafting and publishing packs.
  • Each person sees their part and can do only their partThe GM password and its login token; a watch-only pass for the Pi 4 scoreboard; anonymous player scans.
  • The game fits the venue it is in tonightVenue profiles and "not installed tonight"; standalone modes on the GM tablet and the phone's scanner; the blue and green machine method: a new show machine is built beside the one in use and swapped in by replugging.
  • Anyone reading a screen can act on it without a second questionHealth words healthy, down and not installed tonight (grey) for each service on the health panel; a first, minimal preflight.
  • A change is proven before it reaches anyone, and the owner alone sends it to the showAutomated tests at four levels, from single pieces of code to the whole system in a browser; an automatic test run of the real engine and its programs, at the level of real programs with stand-in hardware, started by hand or by a change to its own files (the standing test rig was lost when the cloud computer it ran on was wiped; its recipe survives, and the rig is built again when the build half starts); an automatic test run on every proposed change before it joins the main code; and a rule that the share of code the tests reach may not fall.

The pieces already well built

  • The hardening block's merged pieces stay in the engine and change only where a design choice requires: the equipment families, the core that marks equipment not installed tonight, and the smallest test set-up (Corrections to the readers and the hardening pieces).
  • Blue, the show machine in use now, runs every show until the new engine is ready; its fixes and the problems found in it are evidence of where today's design is weak, never the reason for a design (Blue's fixes are evidence of design causes).

Mainly touchesThe designer's game is the game the whole kit plays

Pack edits reach each copy of the pack differently

20 problems found

Touches the architecture pass questions on what each fact does between games, on whether one question gets one answer, and on how copies update and whether a screen shows their age.

At a show A designer publishes a pack change and does not restart. The TV shows evidence by the new rules while the engine scores by the old. The file the engine hands out no longer matches the fingerprint in the engine's own pack list, so a scanner that checks rejects it. A tablet running a different pack is only noted in the engine's log; nothing tells the GM. The publish tells the running engine nothing.

Why it happens The engine freezes one pack at start, yet the files it hands out are whatever is on disk now, and it re-reads the token list from disk at every request. The TV, tablet and hardware scanner each load the pack at their own moment and keep it; the phone reads its own copy. No message says it changed.

In a standalone game Each device loads whatever pack its source holds; a mid-game reload can hand the tablet a newer pack; nothing marks which pack version the game or any device has. In the candidate each device shows its pack version, the Game record carries the game's, and Lifecycle refuses a swap mid-game. The other way, an engine of its own on the tablet, must do the same, kept equal by tests.

How the earlier candidate would remove it
Removed by these parts of the earlier candidatePack channelDesign studio

In design terms The Pack channel should own one loaded pack behind one interface: load, say which is current, hand out a file, announce a change. Each place a pack comes from is an adapter at its seam, and the Design studio reaches the engine's copy only by sending it requests. Today both the copy the engine froze at start and the files on disk under it cross the seam: no locality.

The problems behind it, and the code they live in
  • After a pack edit with no restart, the engine hands out the new files while it scores from the old pack; the files' fingerprints no longer match its list.
  • Publishing a pack from the config tool tells the running engine nothing; the engine scores by the edit only after a restart.
  • A tablet or scanner on a different pack than the engine is only logged; nothing tells the device or GM.
  • Before a restart the TV shows evidence by the new rules while the engine scores by the old.
  • A new pack reaches a hardware scanner only after a reboot; tokens cannot be re-synced by command.
  • A password changed in the config tool's settings editor works at once on the tool, and on the engine only after a restart.

Each tablet keeps its own list of claimed tokens

19 problems foundA fix on blue points here

Touches the architecture pass questions on who decides each fact and on how copies update and whether a screen shows their age.

At a show A GM deletes a transaction. The engine frees the token, but every tablet that stays connected keeps refusing it as already scanned until someone reloads. A tablet that drops its connection during Reset All Scores comes back still holding the old claims, and refuses tokens the engine has cleared.

Why it happens The engine decides which tokens are claimed, but each tablet holds a copy that only grows: added on scan, merged on reconnect, removed only when a scan fails. The engine's own messages also skip facts that change as a side effect of something else, such as a team created by a scan.

In a standalone game One tablet holds the only list, but not every screen refreshes. Two standalone tablets are two separate games; one per game is undecided. In the candidate shape the tablet runs the engine's Game record and Lifecycle; or an engine of its own, kept equal by tests.

How the earlier candidate would remove it
Removed by these parts of the earlier candidateGame recordLifecycle

In design terms The Game record should own which tokens are claimed, read from the transactions. Delivery's interface is the one seam between a claim and a screen; each tablet is a Screens adapter drawing it. Today the tablet updates its copy with one hand-written step per message; a message with no step leaves it stale: no locality.

The problems behind it, and the code they live in
  • GM deletes a transaction; every connected tablet keeps refusing the token as already scanned until it reloads.
  • A tablet that dropped its connection during Reset All Scores reconnects with its stale claims and refuses cleared tokens.
  • After a reload a tablet knows only its own claims; a rescan of another station's token shows success, then rejection.
  • A delete recomputes every team's score but the message carries one team's row; no screen shows the fault yet.
  • A scan for a team nobody added creates the team silently; no team message reaches any tablet.
  • Session Details freezes Teams and GM Stations at the last full catch-up, because one message adds to the list and the other replaces it.

Reconnect snapshot and live update are built apart

11 problems found

Touches the architecture pass questions on whether the catch-up after a reconnect matches the live message and on how copies update and whether a screen shows their age.

At a show A GM reloads a tablet mid-game. The History badge stays hidden until the next scan, and a rebuilt admin panel can show the clock as --:-- until the next change. The device list flips between every device ever seen and only those connected now, depending on which message came last.

Why it happens For each fact the engine has one piece of code that writes the catch-up a tablet gets when it connects and another that writes the live message, and six places send the catch-up with hand-picked contents. The tablet applies each by a different rule, and a restore after a reload sends screens none of the notices they wait for before they redraw.

In a standalone game There is no catch-up on reconnect. Reading the saved game back at a reload tells no screen, so the History badge stays hidden. In the candidate the tablet's Lifecycle and Delivery send a restore like a change; or an engine of its own, kept equal by tests.

How the earlier candidate would remove it
Removed by these parts of the earlier candidateDeliveryLifecycle

In design terms Delivery should own one piece of code per fact, building the catch-up and the live message from each deciding part's changes; Lifecycle's restore sends the same, and Screens draws only what that interface defines. Today the code that builds the catch-up is shallow: whoever uses it must hand it every module, and five adapters on the tablet reshape what it builds: no locality.

The problems behind it, and the code they live in
  • After a reload the History badge stays hidden until the next scan; the restore path fires no event.
  • After a panel rebuild the first live message can be missed and the clock shows --:--.
  • The device list alternates between everyone ever and connected only, depending on which message came last.
  • Six places send the full catch-up and disagree on which devices to include and which extra items to add.
  • The catch-up and the live message come in different formats for the clock and cues; five adapters reshape them, and the clock's adapter loses the values it does not name.
  • A TV reloaded during a video shows its last overlay state, because the catch-up's display state is never read.

Tablets and phones decide facts the engine owns

19 problems found

Touches the architecture pass questions on who decides each fact and on whether one question gets one answer.

At a show A GM scans a token; the result screen says Transaction Complete with points the tablet worked out itself, before the engine has answered. The engine may refuse, and the correction arrives as a small pop-up message. In a standalone game the tablet is the only judge, and its rules have gaps: a scan into a paused game shows complete and records nothing. A phone says revisited for last week's token.

Why it happens The engine decides scoring, claims and whether a scan is allowed now, but the tablet carries its own copy of those rules, kept matching by hand, with a note in the code as the only reminder. The phone and the hardware scanner each choose a team on their own and decide on their own whether a token is new or already seen. Each device shows its own answer first.

In a standalone game The GM tablet judges claims, scores and scan permission from hand-kept rules; each player device decides whether a token is known. In the candidate shape the tablet hosts the engine's Game record, or an engine kept equal by tests; player devices share one rule, sent to them as a table rather than written into each app.

How the earlier candidate would remove it
Removed by these parts of the earlier candidateGame recordGame rulesScreens

In design terms The Game record should own every outcome a tap gets, running Game rules as one body the engine and the tablet both load. Answering's interface is the seam a tap crosses; Screens draws the reply. Today the tablet keeps its own copy of the rules, so a rule change lands in two places: no locality.

The problems behind it, and the code they live in
  • Result screen says Transaction Complete with tablet-computed points before the engine answers; the engine may refuse.
  • Standalone: a scan into a paused game shows complete, records nothing and locks the token until a reload; an ended game still accepts.
  • A duplicate scan on the same tablet never names the team that claimed it; the tablet's own check refuses it first.
  • Every player scan carries a team no game declared; the engine discards it and only logs it.
  • A phone that played last week still says revisited for a token in tonight's game.
  • The tablet matches token ids loosely, the engine exactly; the tablet shows success and the engine refuses.
  • A sale carries the tablet's clock and a manual adjustment the engine's. The GM enters the first-burial bonus and the transfers as adjustments, so they printed nine hours away from the sales; ALN's Director Console shifts them back.

A reply never says which request, final or stored

18 problems found

Touches the architecture pass questions on who decides each fact and on how copies update and whether a screen shows their age.

At a show Player devices upload their queued scans while no game exists. The engine answers "processed", stores nothing, and both devices delete the scans. A GM's scan that can never succeed comes back as a vague error, so the tablet resends it at every reconnect with a pop-up message each time. A slow Reset System reports failure and the new game is skipped.

Why it happens The engine answers before, or without, saving the fact it reports; calls an unsaved batch processed; returns some failures as a named outcome and others as a vague error; and confirms a command by the command's name alone, so two quick presses cannot be told apart. Each device then decides for itself what a reply means.

In a standalone game Each device answers itself and ignores the answer: a refused scan shows Transaction Complete; a queued scan shows as recorded. In the candidate the tablet's Answering shows a refusal as refused; an engine of its own returns the same words, kept equal by tests. The step that saves a scan on each player device returns the same words, from the one list.

How the earlier candidate would remove it
Removed by these parts of the earlier candidateAnswering

In design terms Answering should own one interface, one request in and one reply out, with the two ways a device talks to the engine (a web request, or the live connection a tablet keeps open) as its two adapters; the outcome words are one fixed list every device reads, never written into its code; the Game record saves, then gives Answering the outcome. Today three reply formats leave each device its own rule: no locality.

The problems behind it, and the code they live in
  • Scan failures such as no game or a full queue come back as a vague error; the tablet resends them at every catch-up.
  • A batch of saved scans arriving with no game is answered processed but stored nowhere; both player devices delete it.
  • A batch of saved scans sent again after an engine restart is stored twice; the engine remembers the batches it has processed for an hour, and forgets them when it restarts.
  • A Reset System slower than the tablet's five-second wait reports failure, and the new game that should follow is never created.
  • The engine's reply to a GM command carries only the command's name, success and a message, so two presses of one button are both settled by the first reply.
  • One failed batch is dropped by the phone's scanner on any refusal but kept forever by the hardware scanner.

Nothing says what a game boundary clears or keeps

22 problems foundA fix on blue points here

Touches the architecture pass question on what each fact does between games.

At a show The GM ends the game and restarts the engine; the ended game comes back as the current one and player scans keep landing in it. When the game ends, a tablet that reconnects loses its history and the wall scoreboard goes blank. A once-only cue spent in game one stays spent in game two.

Why it happens Game start, end, reset, engine restart, tablet reload and reconnect: each moment between games has its own code on each device. No table says, for each fact and each copy, whether that moment clears it, keeps it or fetches it again, and no message announces one; screens guess that a new game began when the game's id number changes.

How the earlier candidate would remove it
Removed by these parts of the earlier candidateLifecycle

In design terms Lifecycle should own the table of moments against facts and the one interface that moves a game from one moment to the next by that table; it alone calls every part's reset, and Delivery sends each moment as a fact. Today the session, cue, reset and tablet modules each hold their own cases: no locality.

The problems behind it, and the code they live in
  • An ended game comes back after an engine restart as the current game, and player scans keep landing in it.
  • After the GM ends the game, a reconnecting tablet loses history, scans and Download Report; the wall scoreboard goes blank.
  • A once-only cue spent in one game stays spent in the next unless the GM ran a system reset between.
  • After a reload the tablet wipes the offline scans it just restored, reading the first message as a new game.
  • A system reset empties the engine's video queue to idle while VLC plays on, and the GM is told nothing.
  • Reset System sends no tablet a fresh catch-up; tablets keep the old game's data until a new game id arrives.

Boot and Reset System wire the engine differently

7 problems foundReproduced in a test

Touches the architecture pass question on what each fact does between games.

At a show The GM presses Reset System to recover mid-show. The music panel goes dead until someone restarts the engine. Later, Reset All Scores sends every tablet and the TV the old transaction list, so cleared evidence comes back on the wall. The cues now hear each video and clock event twice, and the Display row stays red until Check Now.

Why it happens Starting the engine and rebuilding it after a reset are two separate hand-written lists. Standalone today

Standalone games today, and the hardware scanner against the phone's scanner with no engine: 24 differences

The decision Standalone games: declared, never mixed adds a requirement: a whole game can run with no engine, the GM tablet and the player scanners each working alone, as a choice the game declares and never mixed. In a standalone game the GM tablet decides everything about the game (used tokens, scores, teams, the game's start, pause and end) from its own hand-kept copies of the engine's rules. Each player scanner decides only whether a token is known, and the phone also whether it has seen that token before.

Four design flaws cause no problem in a standalone game, four apply in part and eight in full. Each promise and each situation says what changes.
