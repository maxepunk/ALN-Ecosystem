Parts

This is a candidate shape for the whole engine, not a decision. Most of today's problems sit in work several promises depend on: getting a fact onto a screen, answering a request, knowing who is connected, the boundary between one game and the next. Each is done several times today, in different places. In the candidate each such piece of work becomes one part, seventeen in all, and the parts already well built today (the game rules, the verdict, the health words) are the pattern for the rest. Step 3 starts from this frame and puts competing designs in front of you; where the map found two sound ways, the last table on this page names both and what each costs.

Each part has a card. What it does says the part's work in plain words. Mainly keeps names the promises the part exists for, and also needed by the promises that use it; each is a link to Promises. Today says how the same work is done now, and removes names the design flaws the part would take away, each a link to Design flaws. Runs on says which devices would host it: the engine, GM tablets, player scanners, the scoreboards, the config tool or the tests; in a standalone game several parts run as small stand-ins on the GM tablet. Where it can be swapped names the part's seams: what plugs into it, and where behaviour can change without touching the rest.

Before the cards come the qualities every part must have, the parts in layers (each part uses only the parts in the rows below it, so nothing loops back) and five moments at a show followed through the parts in order. After them come which part would run where, the tangles where today's code spreads one piece of work over many places, and the choices where a real alternative exists.

Which part would run where

  • The engine would decide every fact of a networked game, serve the pack, admit every connection, answer every request through one door and send every fact to the screens through one route.
  • A GM tablet in a networked game would draw what it is sent, with each fact's label, and send requests in one envelope. It would keep no list of its own and decide nothing before the engine answers. Today it decides before the engine answers.
  • A GM tablet in a standalone game would be the same app with the switch set. In the candidate it runs the same record, lifecycle, answering and delivery parts the engine runs, with small stand-ins that report every engine duty (video, music, lights) as not installed tonight. The other way is an engine of its own, kept equal by tests.
  • The phone and the ESP32 would draw, send scans in one envelope, and read the reply words and the few rules they need as data made from the one source. They would stay equal by sharing that data.
  • The scoreboards would be one page in two places, the TV and the Pi 4, drawing what they are sent and deciding nothing. Today the page decides which modes count as evidence. One page or a view inside the GM app is an open choice for step 3.
  • The config tool would hold the design studio and the venue technician's profile editor, and talk to the running engine only by message. Today it writes the engine's files. A separate program or a surface the engine serves is an open choice for step 3.
  • The tests would run on an engine of their own, with stand-ins for the equipment, and never touch the live one. Today they use the live display and audio.

Where today's code tangles

Where the promises' work sits in today's code: 13 tangles

A tangle is one piece of work spread over many places with nothing joining them, one place doing many kinds of work, or a dependency running the wrong way. Each causes some of the design flaws on Design flaws.

  • The pack is held in nine places and nothing joins them. The engine's frozen snapshot and the live disk bytes under it, the tablet's cache, the phone's own file, the hardware scanner's card, the TV's own fetch, the design tool's working copy, the sync script's output, two nested copies and media in three folders. No message says the pack changed, so after a publish the TV, the engine and a tablet can run three versions of one game. Flaws: C12 C14 N1
  • The game's facts are decided once and re-decided in five parts. The tablet marks a token claimed, computes the points and shows complete before the engine answers; the phone and the hardware scanner decide whether a token exists; the TV decides which modes count as evidence; a standalone tablet decides everything from a hand-kept copy of the rules. Eighteen rules are re-decided on clients, and for five of them nothing keeps the copies equal. Flaws: C1 C9 C11 C6
  • One fact, two builders; state and health on two routes. For seven facts the snapshot a tablet gets on connect and the live message for the same fact are built by different code. A service's state and its health arrive as separate pushes. No fact carries an age, and no screen reads the ages that exist. Flaws: C6 C2 C10
  • Three doors, three reply shapes, acknowledgements matched by name. A player scan, a GM scan and a GM command each get a differently shaped reply. The tablet matches an acknowledgement to a request by the action name alone, so two quick presses cannot be told apart. The phone and the hardware scanner read the same status differently. Flaws: C7
  • Who is connected has no home. The engine asks a pass only of a connection that calls itself a GM; the TV calls itself a GM; the whole game state can be fetched with no pass; a health check registers a device and files a hardware scanner as a phone; the design tool runs a second login against the same password; five clients each draw their own reachability word. Flaws: C13 C10
  • The life of a game is carried in six places and owned by none. Boot and Reset System are two hand-kept lists that differ; nineteen parts each reset themselves and Reset System calls fourteen of them; the record calls into the show from five places and the show calls back, a seven-module loop; the tablet and the TV guess a boundary from a changed id; the player devices' queues outlive every game; the engine undoes its own wiring only under test. Flaws: C4 C5 C1 C6
  • Equipment: seven adapters, no shared interface, a cached picture with no age. Each program is read by parsing its text or its event stream. Whether a video is playing has several answerers; held cues and held videos live in two stores; the music player keeps a private connected flag beside the shared health list; supervision has two shapes. Flaws: C3 C11 C2
  • The engine assumes it owns the machine, and tests assume they may use it. Sixteen fixed temporary names, two machine-wide kills, media folders in fixed places and kit names in at least twelve files. Tests adopt the live display, audio and Bluetooth and write placeholder videos into the live media folder. Flaws: C8 C15
  • The tablet is a command center and a second engine in one, and the standalone choice is not a seam. Four files carry a second copy of the rules; thirty of the tablet's sixty-seven files would carry a standalone game; the one strategy seam covers storage only, and twenty branches in six modules ask the mode directly; the four domain objects reach everything through a back-reference; three layer inversions make dependencies run both ways. Flaws: C9 N1 C14 C11
  • The design tool reaches the engine by file and by import, never by message. It writes the engine's settings, routing file and media folders; imports engine modules by path; runs the engine's pack check as a child process. An edit becomes visible at the engine's next restart. There is no apply step, no preview engine and no statement of where one would run. Flaws: C12 C8
  • Joins kept by hand, fakes unchecked, tests per part. Twelve test configurations by part and three contract tests that pin joins. Nothing checks the hardware scanner's token-file shape against the pack, a fake against its class or the scoreboard's reading of the snapshot. The deployed game is several checkouts, a built folder and hand-copied media that nothing compares. Flaws: C14 C16 C15
  • Shallow chains and thick doors. Skip video crosses five tablet modules to reach one deep one; one command dispatcher serves six promises; the player scan route decides token existence, session existence and video eligibility inline and holds a batch cache lost at restart; the engine's wiring is written by hand at about ten sites, and one of them already left music out. Flaws: C11 C5 C7
  • The scoreboard page is one file, two deployments, and sits on both sides of the engine. Nearly two thousand lines with no module boundary; it decides the evidence rule and the money format from a file it fetched; it extrapolates the countdown and keeps counting after a disconnect; the engine launches, shows, hides and kills its browser as an outside program while the page is a client of the engine under a pass minted into the page text.
