What the engine is for

The engine is the game-independent software that runs a show, and it is going toward an open-source show platform that designers who are not technical can use and technical people can extend.

A game designer builds a whole game as a pack in the design tool, never touching code or configuration files, and tunes it by changing a value, applying it and playing.

A venue technician fills in a profile of what the venue has, connects the pack's names to the real instruments in the room on one page, and runs one preflight that answers go or no-go, with every line showing where its answer comes from.

A GM runs the show from four sections (Game Ops, Show Control, Environment, Game Admin), and the post-game report builds itself from what was captured during play.

A player taps tokens on a phone or a shared station with no account, no login, no app to install and no recorded identity unless the game designs an identification moment.

The business is one production, one kit and many games on it; a second kit or operator is not planned, but must stay cheap to start, so nothing in the engine may assume one kit, one pack or one production. The engine is meant to be open-sourced for many games in many production settings, so it says which requirements are fixed and which each production sets for itself. ALN is the first production: one game, one venue, the hardware the owner bought. The engine does not take ALN's hardware as its own requirements. The mature engine is flexible about hardware; the current roadmap sets how much of that flexibility is built now and where it names specific hardware requirements, and where it draws that line is open.

Some rules hold throughout: players' data stays on the kit; media never lives inside the pack; phones and hardware scanners stay equal; the engine holds no opinion about game design; no technical failure stops a game, and the GMs know their fallbacks at a failure; red always means act now; the preflight states its own limits; nothing deploys to the live machine until the owner says the new engine is ready.

A second, toy game stays with the engine's code for good, so every change is proven on two games and ALN stays one pack among others.

How well it must work

  • Staying up through a live showNo technical failure stops the game: after a power cut, a crashed music player, a dropped tablet or scans sent twice, no scan is lost or doubled, tablets return under their names, held cues show as held, and the GMs see what they can still do.
  • Every screen telling the truthNo screen shows a calm value it cannot confirm: a silent engine reads offline within a set time, old numbers look old, grey means not installed tonight, red means act now, preflight lines say paper or live, and no unanswered scan shows complete.
  • The designer's iteration speedA changed value plays within minutes, with no restart; the desk refuses a broken pack and names the fault; a trial copy never touches the show; a whole game is built in the design tool, with no code or settings file.
  • Operating it without technical helpA venue technician stands the kit up from the guide to one go or no-go, with no terminal; power-on leads to a running show; a dropped speaker gives the GM a red row with its actions; the night's record writes itself, with one clock.
  • Easy to understand and change, for people and for AI agentsEach fact on a screen is decided in one place, and the published protocol states the engine's edge once; a newcomer, person or agent, learns the glossary, promises and protocol in one sitting and proves a small change within a set time; no word of ALN's lives in the engine.
  • Easy to extendA mechanic made from what the engine already does should probably be the game maker's own; an ability it lacks is added once for every game; a new kind of device joins by its pass; a new lighting system or video player changes only its own code and the profile.
  • Testable without the live showA whole game runs on a laptop with stand-ins for the room's equipment, the same at every test level; every change runs on ALN's pack and the toy game's; skipped tests fail loudly; stand-ins are checked against the real thing; no test touches the live show.
  • Privacy and accessPlayers have no account; the engine records only a device or session id unless the game designs an identification moment. Game data stays on the kit for as long as the production sets, and players' email addresses stay outside the engine; strangers on the venue wifi get nothing; only staff who log in control a game; each screen gets only what the engine filters for it.
  • Running well on the show machine and the venue network at the size of a showALN's kit, one show machine with a few tablets, scanners and screens on its own network with no internet, runs a two-hour game with headroom, within the engine's stated times and each production's limits; phone capacity is measured first; a pack stays small, naming its media by fingerprint.
  • Standalone and offlineA game declared standalone says standalone, never disconnected; its tablet decides by the engine's rules, proven equal; no game mixes the two kinds of device; its record names the pack it ran; a scanner that loses the network keeps its scans and sends them once.
  • Safe release and rollbackThe show machine keeps one written list of what it should carry, and a check names any piece that differs; nothing reaches it until you say the new engine is ready; replugging the old machine brings everything back.
  • More than one copy, kit or pack without reworkTwo copies of the engine share one machine without touching each other's files, ports, programs or passes; the operator picks one installed pack per event; a second kit needs only a profile.

The words

The site's own words come first, then the names of the steps of the work, then the words the design rounds use; each situation on Today's engine ends with the reason restated in them.

This site's words

Promise
What a person can count on at a given moment. Parts keep promises; design flaws break them. The ten promises are the first of the requirements.
Moment
When a promise matters: a production stage (Author, Rehearse, Run, Review), a point in a show, or release day.
Quality
Something every part must have so a promise holds everywhere, like every screen telling the truth, or testable without the live show. It keeps promises; it is never a promise or a part. The twelve qualities on this page group the quality targets.
Quality target
One situation under a quality, told so it can be tested: what happens, then what must be true. It says what is needed, never how to build it; where a number is needed, the target says whether the engine states it, each production sets it (with ALN's as the first set), or it is a technical default the agent proposes.
Fixed requirement
Something the engine requires or states the same for every production, whatever its game, venue or kit: the hardware it needs, the network it needs, and the limits it states (the largest kit, how fast it answers). A production cannot change it; it can only check it fits.
A production's setting
Something the engine lets each production set for itself: the devices and phones in its kit, its set-up time, how long it keeps records. ALN's settings are the first set; another production brings its own.
Fallback
What the GMs can still do to keep the game running when something fails mid-show: which actions still work, which wait, and the button or step for each. Your word.
The two kinds of game extension
A mechanic made inside a game from what the engine can already do, which should probably be the game's own maker's work, in your tentative words; or an ability the engine lacks, which probably needs a developer to add it once so that any game can use it.
Extension case
One way the platform must be able to grow, told as a situation: who does the growing, what they should need to touch, and what must stay untouched.
The standing rules
The roadmap's rules that bind every block: players never have accounts; the engine's only built-in identity is the device or session id, and naming a person is game policy, never an engine default; game data stays on the kit, and how long it is kept is your decision, per game; media never lives inside the pack; a game is playtested with no code or settings file, by changing a value in the tool, applying it and playing it; phones and hardware scanners stay equal in what the engine lets them do, not in their screens; the engine holds no opinion about game design; nothing assumes one kit, one pack or one production.
Design flaw
Something in today's design that breaks a promise. The sixteen are test situations any new design must handle, never the reason for a design.
The published protocol
One versioned definition of everything that crosses the engine's edge: what a device may ask, what the engine answers, what it tells screens, and the files that carry a game or a night (the pack, the venue profile, the night's record, the media list). Every program's code is generated from it or checked against it. It is designed in an early design round, not merely collected.
The pack
A whole game as data: its tokens and their content, modes, scoring, groups, cues, the clock, its words and its look, written in the design tool and published through the engine's check that refuses a broken pack. Media files are not inside it; the pack names them by a fingerprint of their content.
The venue profile
What the room has tonight, filled in by the venue technician: which speakers, which lights, which network, how many stations and screens, and which real instrument each of the pack's names binds to. A second venue is a second profile; the pack is the same.
The night's record
The one record the engine writes when a game ends: the facts it decided, with the roster, the notes, the accusation and the photos captured during play, the pack and version the game ran, and the texts the players saw. The director tells the night from it.
Media list and media bundle
The pack's list of its media files, each named by a fingerprint of its content, and the bundle that carries the files themselves and moves between machines; a missing or changed file is named before the show.
The earlier candidate
The 17-part shape of the engine drawn bottom-up from today's engine, on this site since version 5. It is one input among the panel's: the panel compares it with its own proposals in its second round. Nothing in it is decided.
Part
One of the 17 pieces of the earlier candidate. It runs on the engine or on a device.
Architecture pass questions
The nine questions the architecture pass asks of the whole engine: who decides each fact the GM sees; whether a service's state travels with its health; how the engine reads the programs it runs; whether anything but the live engine can touch the live show; whether one question gets one answer; what each fact does between games (a start, an end, a reset, a restart, a pack change); whether each screen gets only what its role needs; how copies update and whether a screen shows their age; and whether the catch-up after a reconnect matches the live message. Since the design rounds go by the hardest decisions to reverse, the nine serve as checks on each design; the agent confirms that reading as its call, on Decisions, for you to overrule. They are not the questions on Decisions, which wait for your answer.
Venue technician
The person who fits a kit to a venue: fills in the venue profile, binds the pack's names to the real instruments in the room, and runs the preflight.
Director
The person who tells the night's story at the Review stage and carries what was learned back into Author; usually the same person as the GM or the designer.
Paper or live
Checked from the files only, or checked against the equipment in the room.
A device's pass
What a device shows when it connects: who it is and what it may do.
Not installed tonight
Grey, absent on purpose, never a fault: tonight's profile leaves the service out. The code calls this state dormant. A service the GM takes out of service during the show is dormant too, for its own reason, and reads “Out of service”, also grey.
Health words
Healthy, down and not installed tonight (grey): the three words every service's health is reported in.
Label
What every fact and every reply carries to a screen: how old it is and how sure the engine is of it, so a screen can show “old” or “unknown” instead of a calm normal value.
The show machine in use now, the new show machine
The show machine in use now is left untouched by this work; the game runs on it until the new engine is ready. The new show machine is the one this work builds. Swapping in the new machine is done by replugging, and replugging swaps back.
The toy game
A small second game kept beside ALN for good, so the engine is always tested on a game that is not ALN. It also shows a new designer how a game is made.
Planned capability
One thing the engine is planned to be able to do, such as restarting a crashed program by itself. A list drawn from the roadmap you approved names 52; each promise shows the ones that need something from it.
The test bench
The developer's tests, kept outside the engine, where a thin first version of the new design runs end to end at the start of the build half. The tests run the same engine, the same pack and the same checks at every test level.
The test rig
An automated machine that runs the real engine with the real video, music, audio and lighting programs and stand-ins for the room's equipment, so a design flaw can be made to happen for real instead of being read off the code. It was lost when the cloud computer it ran on was wiped; it is built again when the build half starts, as part of the test bench, not before design.
Pi 4
The small computer that shows the scoreboard on a second screen.

Question rounds

The words the design rounds use

Module
Any piece of code with an inside and an outside, from one function to the whole engine.
Interface
Everything other code must know to use a module.
Seam
Where one module meets another, and where behaviour can be swapped.
Deep, shallow
A deep module does a lot behind a small interface. A shallow one makes its callers know almost as much as it does.
Locality
