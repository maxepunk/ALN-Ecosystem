Where the qualities pull against each other

The quality targets on Requirements fall under twelve qualities. In the top-level design some of them pull against each other. The requirements already answer most of those conflicts. Each line below names the two sides, then the conflict, the answer, and what the answer rests on: a decision of yours, a ruling in the roadmap, or a target still marked proposed or partly settled, which you can flag in the review below. The panel designs to them as they stand:

The designer's iteration speed against the promise “Each lifecycle button does exactly what its name says”. The conflict: the designer wants a changed value to play at once, and the GM needs a running game to stay the game it started as. The answer: a change reaches a game only between games, or the engine refuses and says why (A published change plays within minutes, Change one value between shows and play it). It rests on the roadmap's design-iteration loop and on your ratification of the design tool's pages.

The designer's iteration speed against safe release and rollback. The conflict: packs change often and the engine changes rarely, so a pack can ask for something this engine cannot do. The answer: packs publish at any time; the engine changes only between events; a pack that needs an ability this engine lacks is refused at publish with the ability named (A release can be undone before the next game, A broken pack is refused at the desk, New abilities for a second game break nothing). It rests on the roadmap's rulings. One part is open: whether a pack built for an older engine must always open on a newer one. It is in the question “Release day: what must update together, and how long older devices work”.

Standalone and offline against easy to understand and change. The conflict: a standalone tablet decides the game with no show machine, so the game's rules run in a second place. The answer: a game is declared networked or standalone and never mixes the two, so no game ever has some devices on a show machine and some alone. It rests on your decision “Standalone games: declared, never mixed”. Whether one standalone game may use more than one GM tablet is the question “Which standalone games the engine must run”. Whether the show machine and a tablet run one body of rules or two kept equal by tests is a later choice for the design rounds.

Privacy and access against staying up through a live show. The conflict: every request is checked against a pass, and a restart could make every pass invalid and send the GMs back to the login screen mid-show. The answer the agent proposes: a pass holds through a reconnect and a restart of the engine, and nobody logs in again during a show. It is a proposed addition to “Every request is checked against its pass”, for your review. Whether a pass holds when the show machine is changed is for the design rounds.

Privacy and access against the promise that the night can be told afterwards. The conflict: the director needs the night's record to tell the night, and the players' data should not leave the kit. The answer: game data stays on the kit, you move the record when you choose, and the Director Console stays a separate program outside the engine (Game data stays on the kit). It rests on your decision “The night's record and the after-game article” and on the roadmap's rules on player data.

Operating without technical help against privacy and access. The conflict: checks need passwords and passes, and a GM with no technician must not manage them. The answer: devices get their passes by themselves and never show a login, which is a standing rule; only staff who log in hold the game's controls, by your ruling of 2026-07-09; and a GM logs in once before the show, which the agent proposes (Power on straight into a running show, Every request is checked against its pass).

Running well at the size of a show against more than one copy, kit or pack. The conflict: a second copy of the engine on the show machine shares its processor, memory and heat with the show. The answer so far covers size only: a few dozen devices is the setting the panel gets (What the architects' panel sees, and when), and phones are measured before the first is admitted (Phone capacity is measured before the first phone). Whether a second copy of the engine may run on the show machine during a show is open. It is the question “Where the trial copy runs while a show runs”.

Testable without the live show against easy to extend. The conflict: an extension is quicker to add with no stand-in, and then the show cannot be tested without that equipment. The answer: every added program or device kind comes with a software stand-in and its tests (A different lighting system or video player, Every test runs twice and never skips silently). It rests on the glossary's entries on software stand-ins and on running every test on two games; the case is marked partly settled.

Every screen telling the truth against standalone and offline. The conflict: with no show machine, every service the show machine runs is missing, and a screen could show that as a fault. The answer: a standalone game says standalone, and each such service reads not installed tonight, grey (A standalone game is normal, never a fault). It rests on your decision “Standalone games: declared, never mixed”.

Privacy and access against standalone and offline. The conflict: a standalone device holds everything it can show, so nothing can be kept from the person holding it. The answer: a game with hidden facts needs the show machine, and its pack says so (The owner's second game needs new modules). It rests on the roadmap's block for the second game's modules.

A. A GM tablet cut off from the engine

When to answer Best answered now. It is a call about your show.

What it decides

Staying up through a live show against every screen telling the truth, and against easy to understand and change. Each fallback is more code that runs only at a failure and must be tested and kept working for years. What a GM tablet does with a scan while it cannot reach the engine for a short time, a dropped wifi or an engine restart. What the GM may tell the team at that moment. What happens when the connection returns and the engine disagrees with what the tablet showed. This question is about a short gap, a minute or a few. If the connection does not come back, the GMs choose a fallback, and what a tablet shows from then on is in the question “The show machine fails mid-game”.

What it means in practice
  • Your decision settles that the game goes on (No technical failure stops a game), and the quality target A refused scan never reads as complete proposes that a refused scan never reads as complete; you settled that only for a standalone game, and the networked part is proposed. Open: what the tablet shows meanwhile.
  • At a show. The tablet's wifi drops for a minute. A team hands the GM a token. Today the tablet shows “Transaction Complete” with points, from its own copy of the rules, and keeps the scan to send to the engine later (Tablets and phones decide facts the engine owns). If another tablet sold the same token during that minute, the engine refuses the kept scan on reconnect, and the GM has already told the team it earned money. The quality target A tablet reconnects to the same facts asks that the game carries on and that the GM can always see what became of such a scan, and leaves what the tablet does with it meanwhile to this question.
  • How often two tablets can disagree. A token is one physical object. Two tablets can both claim it during a gap only if someone carries it from one GM to the other inside that gap. If your GMs keep a token once it is sold or exposed, that cannot happen at your shows. Few results could then be overturned: a scan into a game someone paused or ended meanwhile, a sale someone deleted, and a group bonus the tablet could not see. The agent found nothing in the record on whether your GMs keep the token. Tell us which is true.
  • For the GM at the failure. With a refusal the GM says “give me a minute, the connection is down” and the line waits. With a kept scan the GM says “it is in, your result shows when we are back”. With a result shown at once the GM says “you earned fifty thousand” and may have to take it back. Your words are that pausing a game for a lost connection is the worst scenario, and that the GMs need to know their fallbacks. The question is what the fallback shows.
  • For the designer. Nothing changes in the pack. A designer of a game with group bonuses should know that a bonus shown before the engine confirms it can be taken back.
  • For a production adopting the engine. A venue with worse wifi than yours makes this the common case. A production with one GM tablet can never have a conflict between tablets. For them a result shown at once is never taken back for that reason, so keeping the scan with no result makes their teams wait with nothing gained. A production with four tablets can have a conflict when the wifi drops, and only if one token reaches two tables during the gap.
  • Who wins a conflict is the agent's call, listed below: first come, first served, as the engine rules today (“Who wins when two tablets claimed one token while apart”). The later scan becomes a red row with its reason, and the GM can overrule it.
  • Which decision ahead depends on it. “Where authority lives across devices, offline and standalone included” names this question in what it decides. Refusal means the engine is the only decider and tablets are screens. Keep-and-label means the protocol has a provisional state and the engine decides kept scans in a stated order. Results shown at once mean the rules run in two places and the engine can overturn what a tablet showed. “The published protocol's form” follows: what every reply carries (how sure the engine is) depends on whether provisional replies exist. “How the engine holds the game's state” follows too, since kept scans must be ordered against the engine's record.

A tablet reconnects to the same facts, A refused scan never reads as complete, A standalone game is normal, never a fault, Tablets and phones decide facts the engine owns, and the finding of the two clocks under The night's record and the after-game article. The options

  • Refuse while cut off.

    What it means The GM sees a plain reason and nothing is kept; teams wait. The engine is the only decider, the tablet holds no game fact of its own, and the protocol needs no “not yet decided” state.

    What it costs Every wifi drop costs show time, which is close to the pause you called the worst scenario.

  • Keep and label.

    What it means The tablet records the scan as kept and not yet decided, shows no points, and shows the GM a list of kept scans. A team hears no result until the engine is back. On reconnect the engine decides each in order and the tablet shows the final answer; a kept scan refused later becomes a red row the GM must act on. GMs learn one habit: “in, pending”.

    What it costs The protocol carries a provisional state in replies and in the tablet's list, and the engine decides kept scans in a stated order (the agent's call “Who wins when two tablets claimed one token while apart”).

  • Keep and decide provisionally under the shared rules.

    What it means The tablet applies the same rules the engine would, from its last known copy of the game, and shows the verdict and the points marked “not yet confirmed”. The engine confirms or overturns on reconnect. The richest fallback for the GM.

    What it costs Every result the tablet shows is marked “not yet confirmed”, and a screen shows the GM each result the engine overturned. The tablet must already run the game's rules for standalone games (A standalone game is normal, never a fault), so this option adds little to build. Its cost is at the table: a GM may have to take back a result a team already heard, a group bonus included.

What we need from you

Whether a GM may tell a team its result before the engine has confirmed it, knowing that a few results may be taken back. If yes, the tablet shows the result at once, marked “not yet confirmed”. If no, the tablet shows “kept” and the team waits until the connection is back. Neither answer is the first option, refusing while cut off. The agent does not put it forward, because during every wifi drop the GMs can then take no scan at all. Say so if you want it. The agent leans to no for a short gap, because a result taken back costs a GM more than a short wait. If your GMs keep each token they take, almost no result would be taken back, and showing results at once costs little. Your words ask for as little effect on the players as possible, and they can be read for either answer.

B. The show machine fails mid-game

When to answer Best answered now: which of the two. How long the players may wait can wait for the panel.

What it decides

Staying up through a live show against standalone and offline, against every screen telling the truth, and against easy to understand and change. Each fallback is more code that runs only at a failure and must be tested and kept working for years. What a networked game does when the show machine stops and does not come back for the rest of the night. What fallbacks the GMs must have in front of them at that moment. What the players may lose, and what they must never lose. How the results come back together afterwards. The same fallback serves when the kit's network fails for the night and the show machine keeps running. The room carries on by its clock, every tablet and scanner is cut off, and the scores on the TV stop changing.

What it means in practice
  • Settled: no game mixes networked and standalone devices, and the game must go on (Standalone games: declared, never mixed, No technical failure stops a game). Settled for the players' own devices: a scanner shows the player that a scan is kept and not yet sent, and never promises a video it cannot start (Offline scans are kept and sent once). Open: how the game goes on.
  • At a show. Fifty minutes in, the show machine's power supply dies. The TV goes dark, because the show machine drives it. The second scoreboard screen keeps the last scores and evidence it had, says offline, and its clock keeps counting by itself. The music stops. The players' phones and the hardware scanners stop sending; the hardware scanner keeps each scan on its card, shows a red Disconnected, and for a video token says rescan later, which cannot work; the phones say offline. Each player scanner keeps up to 100 scans and then drops the oldest without saying so. The GM tablets lose the engine. Today each tablet has its own copy of the game as of the last message and keeps scanning with its own verdict. Nothing merges two tablets' records afterwards, and no spare takes over.
  • For the GM at the failure. Your words: the GMs need to know their available fallbacks. The tablet should show them as a red row with actions, the pattern Every red row carries its own actions settles. Which actions exist is this question. “Carry on from this tablet.” “Switch to the spare.” “End the game from here.” Which of them the engine offers follows from your answer.
  • For the designer. Cues stop with the machine. The designer must know which effects die with it: video, music, sound, lights, the TV, and the cues and phases that run on the game's clock. A standalone game gives up the same room effects, set out in the introduction to the standalone group below.
  • For a production adopting the engine. A production with no spare machine. A production whose show is mostly the TV, for whom carrying on means little. A production that runs two games a night and cannot afford a lost one. Each would choose differently; the engine must say which fallbacks it offers.
  • For you. After the swap to the new engine you own two show machines: the new one and the old one, which the roadmap keeps as the rollback and then as the test machine. A spare for ALN needs nothing new bought. It needs the second machine set to tonight's release, pack and venue profile before each show, and brought along. One second machine cannot be the spare, the rollback machine and the test machine on the same night.
  • For the players. You asked for as little effect on the player experience as possible. The design cannot promise the TV and the videos without a second machine, and even then only when a GM moves them to it or the kit connects them to both. What the players lose for the rest of the night follows from the answer you give. What they must never lose, as the agent reads it, is their scans counted exactly once and no team paid twice for one token. Say if more must be protected.
  • How often. The agent has found no record of the show machine failing for good during one of your shows. Say if it has.
  • For a game that needs the show machine by its nature. Your second game keeps hidden facts on the show machine and shows a live public screen. If its machine dies, tablets cannot carry it on. For such a game the choice is a second machine or an orderly end.
  • Which decision ahead depends on it. “How the engine holds the game's state”, the first and hardest to reverse. A spare that takes over needs a copy of the game kept somewhere other than the first machine; carrying on from tablets needs tablets that hold enough of the game to finish it; a single store on one machine serves neither. “Where authority lives across devices, offline and standalone included” follows: whether a tablet or a spare may become the decider, and when. “How one engine runs as many separate copies” follows: a spare is a copy of the engine that takes the show's place. “The published protocol's form” follows: how a device finds the engine again on another machine, and whether a pass issued by one machine holds on another.

The options

  • The game finishes on the tablets.

    What it means The GMs keep taking scans and end the game from a tablet. Each tablet shows each result at once, from its own copy of the game, whatever you answer for a short gap. With more than one tablet, each counts only its own sales: a team's full score, its group bonuses and any token claimed at two tables are known only when the tablets' records are joined after the game. The night's record is put together from the tablets and the player scanners. Video, music, sound, lights, the TV and the cues on the clock are gone for the rest of the night. Today a cut-off tablet goes on counting the clock on its own screen from the last value the show machine sent. It cannot move the game's phases, pause the clock or end the game, because the show machine does all three. So the GMs call the phases and the end themselves unless the design gives a tablet the clock.

    What it costs Each tablet holds enough of the game to finish it, and the records of several tablets are joined afterwards. No extra equipment. The GMs rehearse it.

  • The game comes back on a second machine.

    What it means As the first, and a spare show machine in the kit takes the game over, by itself or when a GM starts it. Tablets and scanners find it, and scores are shared again. The TV, the sound and the lights run from the first machine, so they come back only when a GM moves them to the spare, or if the kit connects them to both.

    What it costs A spare in the kit, set to tonight's release, pack and venue profile. A copy of the game kept somewhere other than the first machine. One more thing the GMs rehearse.

    What it costs The show stops.

C. Release day: what must update together, and how long older devices work

When to answer Best answered now: whether a scanner that missed its update must work tonight, and whether an old pack must always open. The length of the window can wait for the panel.

What it decides

Safe release and rollback against easy to extend and operating without technical help. Whether a new version of the engine requires every device to be at the matching version (everything updates together), or the engine must keep working with older GM tablets, phones and hardware scanners for a stated time. How long that time is. Whether a mismatch refuses the device or warns the GM. Whether a pack built for an older engine must always open on a newer one. Whom the promise is for: your kit, or every adopter's.

What it means in practice
  • You said yes, generally, to everything updating together, and asked what the question means in practice and how it affects the design and the build, especially in the long term once the new engine runs ALN. The explanation follows. Settled already: the show machine keeps one written list of what it should carry and names any piece that differs (The machine matches what it should carry); at the first swap, replugging the old machine undoes the release (A release can be undone before the next game). Proposed: every later release can be undone the same night. Open: what happens to the piece that differs, and for how long an older piece works.
  • What the two phrases mean. “Everything updates together” means one release moves the engine, the GM tablet's app, the phones' page, the hardware scanners' firmware and the protocol between them, and the engine refuses anything at another version. “Older versions keep working with a newer engine” means the engine accepts a device from an earlier release for a stated time, and the protocol is built so that it can. Packs have their own rule, below.
  • Today, the GM tablet's app. The engine serves it, so a tablet that reloads after the engine is updated gets the new app. But a tablet that was open before the update, or one holding the app in its browser's cache, keeps running the old app against the new engine until it reloads. At connection the tablet sends its app version and the fingerprint of the pack it loaded; the engine records the version, uses it only to label the station in its list, and writes a pack mismatch to its log only (Pack edits reach each copy of the pack differently). The list of messages the tablet listens for is kept by hand in the tablet's code; a message the engine adds and the tablet does not know never arrives, with no error (Names joining two places are kept by hand).
  • Today, the phones' page and the hardware scanners. In a networked game the engine serves the phones' page too, straight from the page's own folder; the page caches itself under a name that must be changed by hand to make phones refresh. The hardware scanners' firmware changes only by cable; the board leaves no room for an update over the air. Their token list, pictures and sounds sync at boot from the engine. So a hardware scanner is the device most likely to be older than the engine, and a change to the token file it reads breaks every scanner that was not flashed.
  • Today, packs and the protocol. Packs are published separately, at any time. The engine refuses a pack whose format version does not match exactly, a pack that requires an ability the engine lacks, and a pack that names a minimum engine version the engine does not meet; the GM tablet applies only the exact format check. The protocol is two written lists (web requests and live messages), the pack's formats and the venue profile's format, checked by a few tests, and every program copies the names by hand. So today nothing enforces “together” and nothing promises “older works”. Mixtures happen silently: a rollback can leave the machine running pieces from two releases (The deployed game is many parts nothing compares), and a tablet at the wrong version is a log line.
  • In the long term, for your kit. Once the new engine runs ALN, your kit updates between events. The first swap follows the method you ratified: build the new machine, check it against one written list of what it should carry (The machine matches what it should carry), rehearse, swap by replugging (A new engine version reaches the kit and can be taken back). How each later release is put on the kit and taken back is for the design rounds. The pieces that can still lag behind the engine on a show night are the hardware scanners (cable), tablets that did not reload, the standalone phone page's own copy of the pack (which changes only when the page is republished), and packs published later than the engine. The published protocol is what makes each of these either refused or tolerated. In a standalone game nothing compares versions. Each device shows the version of the pack it holds, as the pack promise asks, and nothing refuses a device that is behind.
  • In the long term, for adopters. Other productions have their own release pace, their own fleets of cable-updated devices, and perhaps add-ons or their own builds (the question “How an extension for all games reaches a production”). They build against the protocol and the pack format (One published protocol and an outside test bench). For them, a protocol that may change shape at every release with no window is a reason not to adopt, or to copy and freeze. A protocol with a window is a promise you must keep for years.
  • At a show, under each answer. A hardware scanner missed its cable update and connects to the new engine. Under everything-together the engine refuses it, the GM's tablet names it, and the scanner is useless tonight unless someone has a cable and a laptop. Under a window it works tonight and the GM's tablet shows “older firmware, update before the next show”. Packs. A pack that needs an ability this engine lacks is refused at publish with the ability named (A broken pack is refused at the desk). That covers a new pack on an older engine. It does not cover an old pack on a newer engine. Today the engine refuses any pack whose format is not exactly its own, so a game built two releases ago stops opening on the day the format changes.
  • What undoing a release needs. If a new version fails and you go back to the one before, every hardware scanner already updated for the new version meets the older engine. If the release changed the scanner's program, then under everything-together the older engine refuses them all, and going back takes a cable and a laptop for each scanner. So a release that can be undone the same night needs the engine to accept a scanner one version newer or older. The same holds at the first swap: if you go back to today's engine, scanners already updated for the new engine must still work with it, or be updated back.
  • The night's record. The night's record is a file that is kept. A record written this year must still open after later releases, in the engine and in the Director Console, whatever you answer here.
  • How the answer changes the protocol and the build. Under everything-together the protocol has one version number for the whole release; messages may change shape freely between releases, since no two versions ever meet; code on every side is generated from one definition per release; the test bench tests one combination; and the hardware scanners must be at the release before the show, which means either a cable step on the pre-show checklist at every release or a firmware update over the kit's network at boot, which the design rounds would have to add and which has its own cost (room on the scanner for two copies of its program, a fallback that cannot leave the board unable to start). Under a window every message carries its version; inside the window changes are additive (fields are added, never removed or renamed, and a device ignores what it does not know); the engine accepts the current version and a stated number of earlier ones and tells the GM which devices are behind; the test bench runs the engine against each supported device version, a set of combinations that grows with the window; and a written rule says when a version is dropped.
  • Which decision ahead depends on it. “The published protocol's form” says in what it decides that it settles the version rules; the item above is what each answer does to them. “How today's engine moves to the new design” follows in part: the swap from the show machine in use now to the new show machine is itself a release, and whether old devices may meet the new engine during the move depends on this.
