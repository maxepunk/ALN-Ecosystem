Decided directions

The published protocol

The published protocol is one written definition of everything that crosses the engine's edge, kept in one place with a version number. It defines what a device may ask (“this team turns in this token”, “start the game”, “play this video”); what the engine answers (done; refused, and why; held for later; try again); what the engine tells screens (the scores, the clock, what is playing, each service's health, each with how old and how sure it is); and the files that carry a game or a night (the pack, the venue profile, the night's record, the list of media files).

The code on every side is generated from that one definition or checked against it: the engine, the GM tablet, the phone, the TV and the design tool; the hardware scanner gets its names and its test examples from it. A change starts in the definition. Anything that no longer matches fails when the code is built, not during a show. Version rules say what an older tablet, scanner or pack does when the engine is newer.

It is the line between the engine's inside and everything around it. Inside, the design can be reorganised freely as long as the protocol holds. Outside, everything relies on it: your devices and games, the tools, a future developer, and the Director Console reading the night's record. For an open-source platform, it and the pack format are what other people build against. The other big decisions show up in it. For example, if facts are numbered in order, a reconnecting screen asks for everything after a given number; and if a game is standalone, the tablet speaks the same protocol to whatever runs the game on it. That is why it comes early in the design rounds.

Today the repository has written lists of what crosses the edge: the engine's written lists of web requests, live messages and the night's record, the venue profile's format and the pack formats, checked by a few tests, while every program copies the names by hand. The protocol consolidates and standardizes them, becomes the source of the code, and is designed rather than only collected.

It is not a program that runs. It does not replace the outside programs' own protocols: the video player, the music player and the lighting system keep theirs, and the engine adapts to them inside.

Its cost: generating code for the engine and the web programs, which share one language, and in part for the hardware scanner's program in its own; a version policy; and the discipline that every change starts in the definition. Together with the test bench it replaces the earlier candidate's part Joins and proofs (One published protocol and an outside test bench). Its form is the decision ahead on the protocol's form, above.

The test bench outside the engine

The tests move to a test bench outside the engine (One published protocol and an outside test bench). A test is the engine running with a stand-in venue profile: a profile that binds the pack's names to software stand-ins for video, sound, lights and speakers, which can be generated from the pack's own needs so that every need is met. On the bench a developer runs a whole game end to end on a laptop or a cloud machine with no venue hardware: the engine, the GM tablet's app, both player scanners' software and the TV page.

The same engine, the same pack and the same checks run at every test level (logic only; real programs with stand-in hardware; the home test bed; the venue), and each run records which checks it could not do and why. Which part would run where

  • The engine would decide every fact of a networked game, serve the pack, admit every connection, answer every request in one place and send every fact to the screens through one route.
  • A GM tablet in a networked game would draw what it is sent, with each fact's label, and send requests in one shared format. It would keep no list of its own and decide nothing before the engine answers. Today it decides before the engine answers.
  • A GM tablet in a standalone game would be the same app with its standalone setting on. In the earlier candidate it runs the same record, lifecycle, answering and delivery parts the engine runs, with small stand-ins that report every service the engine runs (video, music, lights) as not installed tonight. The other way is an engine of its own, kept equal by tests.
  • The phone and the hardware scanner would draw, send scans in one shared format, and read the reply words and the few rules they need as data made from the one source. They would stay equal by sharing that data.
  • The scoreboards would be one page in two places, the TV and the Pi 4, drawing what they are sent and deciding nothing. Today the page decides which modes count as evidence. One page or a view inside the GM app is an open choice for the design rounds.
  • The config tool would hold the design studio and the venue technician's profile editor, and talk to the running engine only by sending it requests. Today it writes the engine's files. A separate program or pages the engine itself serves is an open choice for the design rounds.
  • The tests would run on an engine of their own, with stand-ins for the equipment, and never touch the live one. Today they use the live display and audio.
