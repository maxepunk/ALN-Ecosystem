## 2. The local causes

### D-c1. The engine claims machine-wide names, so anything else on the machine collides with it

**Design cause.** The engine finds, owns and ends its helper programs by fixed file names in `/tmp` and by command-line patterns over the whole machine, because it assumes it is the only engine on the box. A test, a rig script or a second (preview) engine therefore shares its identity and ends its children.

**Findings behind it:** D-52, D-56, D-58, D-59, D-64, D-70, D-72, D-73, D-74.

**Other places with this cause** (each read by me). Search: `grep -rnE "pkill|killall|pgrep|/tmp/aln|aln-pm|docker (rm|stop|start|restart|run)|'homeassistant'|rung1-ha" --include=*.js --include=*.sh --include=*.py --include=*.yml . | grep -v node_modules/.worktrees/docs/.test.js/dist/archive`.
- `backend/src/services/vlcMprisService.js:95` (`pgrep -a vlc` sees every VLC on the machine) and `:117` (fixed pid file).
- `backend/src/services/bluetoothService.js:501`, `mprisPlayerBase.js:209`, `audioRoutingService.js:793`, `musicService.js:607`, `displayDriver.js:53`: the other five pid names.
- `backend/src/config/index.js:142`: the Home Assistant container is named `homeassistant` by default; `ha-service.js:20` and `lightingService` act on that name.
- `backend/scripts/desktop-control.sh:14-17`: ends `lxpanel` and `pcmanfm` by name for the whole desktop.
- `backend/scripts/check-health.sh:44,51`: "is the orchestrator / VLC running" answered by `pgrep -f "node.*server.js"` and `pgrep -x cvlc`, i.e. by name over the machine.
- `backend/src/utils/displayDriver.js:104` (window found by the title marker) and the `xdotool` calls at `:289,290,319`.
- `backend/tests/rung1/engine.sh:34-38`: sweeps the same names.

**Candidate design choices (candidate, not decided).**
(a) Every engine instance gets a run directory (and name prefix) from one place; all pid files, MPD paths, sockets and window titles derive from it; machine-wide `pkill` patterns are replaced by killing the process group the engine started. This is blue's `ALN_PIDFILE_DIR` generalised.
(b) A supervisor outside the engine (systemd units or a per-engine container) owns the helper programs; the engine only talks to them, so it never kills by pattern.

### D-c2. No test layer has a declared, enforced limit on what it may touch, and the default is the real machine

**Design cause.** Test layers pick up whatever display, audio, Bluetooth, Home Assistant and media folders exist, and the claims that they are safe live in comments and file names, not in a check. Two layers adopt real resources "ambient first", and several flows opt into the real posture by pinning the venue profile.

**Findings behind it:** D-43, D-46, D-49, D-50, D-51, D-53, D-54, D-55, D-57, D-60, D-61, D-62, D-63, D-65, D-66, D-67, D-68, D-69, D-71, D-75, D-76.

**Other places.** Search: `grep -rnE "displayAlive|pipewireAlive|org\.bluez|reuseExistingServer|0\.0\.0\.0|NODE_TLS_REJECT_UNAUTHORIZED|ENABLE_VIDEO_PLAYBACK|HOME_ASSISTANT_TOKEN" backend/tests backend/jest.config.base.js ALNScanner/playwright.config.js config-tool/playwright.config.js`.
- `backend/jest.config.base.js:11-32`: the safety switches are set only `if (!process.env.X)`, so a developer's own environment overrides them.
- `backend/tests/rung1/provision.js:212-224`: `displayAlive` and `pipewireAlive` probe the machine, not the run's profile.
- `backend/tests/e2e/setup/ha-service.js:76` and `sound-service.js:24`.
- `backend/tests/visual/test_memory_display_css.js:18`: writes `/tmp/aln-visual-test` and needs a running orchestrator.
- `ALNScanner/playwright.config.js:62-65`.

**Candidate design choices (candidate, not decided).**
(a) Each layer declares a capability list (display, audio, Bluetooth, HA, media folders, network bind); a guard in the layer's setup fails the run if anything outside it is touched (blue's leaked-child guard generalised), and the default list is empty.
(b) Run every layer that is not Tier H inside a throwaway namespace (container or user and network namespace) so real resources do not exist for it.

### D-c3. Each client keeps its own copy of the pack and picks up a change on its own schedule; the engine serves live disk bytes under a frozen inventory and announces no change

**Design cause.** The pack is frozen in the engine at start, but the files are served from disk, and every client (TV, web scanner, ESP32, GM, config tool) reads and caches its own copy at its own moment (page load, boot, first fetch). No message says "the pack changed" or "you are behind".

**Findings behind it:** D-02, D-03, D-04, D-05, D-06, D-07, D-08, D-18.

**Other places.** Search: `grep -rnE "tokens\.json|game\.json|pack-manifest\.json|scoring-config" backend/src backend/public config-tool/lib config-tool/server.js aln-memory-scanner/js aln-memory-scanner/sw.js scripts arduino-cyd-player-scanner/ALNScanner_v5`.

(b) Clients stop holding pack files: each fetches the active pack from the engine on every start and treats its copy as disposable; the nested submodule files are removed.

### D-c4. Game boundaries are not messages; each client infers them from whatever arrives

**Design cause.** A game starting, ending, being reset, or the engine restarting is never announced as a boundary. The TV infers one from a new session id, the web scanner has no game link at all, the engine's restore reloads an ended record, and listener order at reset differs from boot, so a snapshot after a reset can carry pre-reset data.

**Findings behind it:** D-10, D-13 (no-game acks), D-30, D-31.

**Other places.** Search: `grep -rn "handleSessionBoundary\|resetForNewSession\|session:update" backend/public ALNScanner/src aln-memory-scanner/js` plus reading `sessionService.js` and `systemReset.js`.
- `backend/public/scoreboard.html:1473-1486,1687-1730`: the id-change boundary; a null session or a restart under the same id is no boundary.
- `ALNScanner/src/network/networkedSession.js:246-259`: the GM clears its queue and claims on an id change (`:251`), the same inference.
- `backend/src/services/systemReset.js:138,162`: reset wires broadcasts before persistence; `backend/src/app.js:206` and `server.js:139` the reverse at boot.
- `backend/src/routes/scanRoutes.js:36-41`: comment says an ended session is null; D-31 shows it is not after a restart.
- `aln-memory-scanner/js/`: no word "session" outside comments (grep).

**Candidate design choices (candidate, not decided).**
(a) A single boundary message with a game epoch number carried on every snapshot and event; each client discards state from an older epoch.
(b) The engine ends a boundary only by sending a full snapshot to every client afterwards (reset and restart included) and clients replace, never merge.

### D-c5. The device decides facts the engine owns: which team, whether a game exists, whether a token is new, whether a scan was recorded

**Design cause.** Player devices keep their own answers to questions the engine is the authority for, and learn the engine's answer only from a scan reply. Their local answers are not tied to the current game.

**Findings behind it:** D-09, D-10, D-17.

**Other places.** Search: `grep -rnE "currentTeam|teamID|scannedTokens|SESSION_NOT_FOUND" aln-memory-scanner/js arduino-cyd-player-scanner/ALNScanner_v5`.

- `aln-memory-scanner/js/app.js:399-405`: whether a token exists decided from the device's file; unknown ids never sent.

**Candidate design choices (candidate, not decided).**

### D-c6. No copy carries an age that a screen reads; liveness is a private timer or poll in each client

**Design cause.** Messages and health entries carry times, but no client uses them; each client decides "connected" or "current" with its own timer (10 s poll, 5-minute silence rule, a tick that runs on), and those windows differ.

**Findings behind it:** D-16, D-21, D-22.

**Other places.** Search: `grep -rn "lastChecked" ALNScanner/src backend/public backend/src` and `grep -rnE "setInterval|setTimeout\(.*[0-9]{4}" backend/public aln-memory-scanner/js`.

**Candidate design choices (candidate, not decided).**
(a) Every message and snapshot row carries the engine's time of last confirmation, and each screen renders "stale" when its newest confirmation is older than a per-fact limit.
(b) The engine sends a heartbeat on every connection with its epoch and time; a client treats a missed heartbeat as the only staleness signal.

### D-c7. A client reads the parts of a snapshot it chooses, and the snapshot and the live update are built by different code

**Design cause.** Each client takes the snapshot keys it wants (the TV ignores display status), asks for a second snapshot, and the engine and its tests build or check snapshot and live shapes separately.

### D-c8. What a component receives is decided by the receiver, and several reads need no login

**Design cause.** The engine broadcasts by room (everything in `gm`) or to all sockets, and serves its whole state to any caller; each client filters. Roles are not an input to what is sent.

**Findings behind it:** D-25, D-26, D-27, D-45.

**Other places.** Search: `grep -rnE "emitWrapped\(io,|io\.emit\(|emitToRoom\(io, '(gm|session)" backend/src` and `grep -rnE "requireAdmin|requireFunction" backend/src/routes`.

### D-c9. A connection's identity is chosen by the client, and the device registry guesses the type from defaults and name prefixes

**Design cause.** Device ids, types and display names are sent by the client or defaulted by a route (`type` absent means player), and special names (`SCOREBOARD_`) switch off checks. The registry therefore cannot say who is connected.

### D-c10. What a scan reply means differs per client, and "acknowledged" is not "stored"
