### Issues

#### Critical (Must Fix)
- none.

#### Important (Should Fix)
1. **`familyInstalled` answers `false` for two of the five equipment families — plan-mandated.** `isInstalled` returns `declared.installed === true` for every non-`audio.sinks` family (endpointServices.js:75-80), but the profile schema gives `stations` the interior `{count}` and `personal` the interior `{expected}` with `additionalProperties: false` — `installed` is not merely absent there, it is ILLEGAL (`backend/config/profiles/installation-profile.schema.json`). `collectPackNeeds` emits an `endpoint` need for every key under `hardware.endpoints` (packNeeds.js:30-35), and the pack-manifest schema leaves that key set open. So a pack that declares `hardware.endpoints.stations` against a profile that declares `stations: {count: 4}` now resolves DORMANT under degrade — or a permanent, unfixable NO-GO under require (resolution.js:100) that only `startAnyway` can pass. Before this change that need resolved `runs` (the old `hasOwnProperty` test). Latent today (ALN declares only the three families; the toy packs likewise), and it follows D3's literal wording ("object family → `installed === true`"), so it is labelled plan-mandated: the fix is a per-family predicate (`stations` → `count > 0`, `personal` → `expected === true`) or an explicit "these two families are always installed-when-declared" branch, plus a unit case for each.

#### Minor (Nice to Have)
2. **`applyDormancy` marks ALL past-due clock cues fired, not the ones that left.** cueEngineService.js:381-391 computes `left` correctly, then calls `this._markPastClockCuesFired(elapsed)` globally. A GM-disabled clock cue whose threshold has passed is swept into `firedClockCues` as collateral, so re-enabling it later will no longer fire it. Only reachable when a cue leaves the dormancy set during an active session (T3's `putInService`), which is why no test catches it.
3. **`service:check`'s two dormant branches disagree.** The single-service branch reports the dormant id as `false` in `resultData` (commandExecutor.js:~905) while the all-services branch omits it entirely and shrinks the denominator (`:940`). Acks no longer forward `result.data`, so this is invisible today — but `validateCommand`'s future readers will see two shapes for one fact.
4. **`processQueue` fails only the head item under a dormant vlc.** videoQueueService.js:~100-115 fails `nextItem` and returns; a restored queue of N pending items drains one per call. The brief's wording is singular, so this matches it, but a `while`/re-entry would empty the queue honestly.
5. **A re-held cue can be re-held forever.** `releaseCue` filters dormant services out of the still-down check and then re-holds on any refusal, so a cue that became dormancy-disabled while held will re-hold on every release attempt (and on every `held:release-all`). `Discard` is the way out; a dormancy refusal arguably deserves an auto-discard rather than a re-hold.
6. **Mis-titled test.** `dormancyService.test.js:224` is named "with no profile loaded, nothing is profile-dormant" and asserts `['audio','lighting','music','sound']` ARE dormant. The assertion is right and the comment above it explains the real intent; the title says the opposite and will mislead the next reader.
7. **One `['healthy','down']` assertion was left two-worded.** `tests/integration/state-synchronization.test.js:143` still pins the old vocabulary (only its neighbouring 8→9 comment was updated), while the E2E twin in `helpers/assertions.js` was widened to three. It passes only because that environment installs everything; a dormant `vlc` there would fail an assertion that is no longer true.
8. **The contract asserts a 300-char `message` bound nothing enforces.** R19's `maxLength: 300` was added at all three health sites, but neither `report()` nor `markDormant()` truncates, so a long service error message would fail schema validation in a contract/E2E run rather than at the producer.
9. **A force-expanded healthy dashboard is labelled `--degraded`.** HealthRenderer.js:155 uses the same root class for "something needs attention" and "the GM opened the summary", so clicking to look at grey rows renders `health-dashboard--degraded` on a venue where nothing is wrong — and the E2E's `--degraded` selector stops meaning "something is wrong". Cosmetic today only because that modifier carries no styling (see 10).
10. **Context, not a defect of this task:** the only `health-*` CSS in `ALNScanner/src/styles/` is the three rules this change added — `health-service--down`, `--ok`, `health-dashboard--degraded` and `health-indicator--*` have no rules anywhere in the tree (grepped `--include=*.css --include=*.html`). "Dormant never renders red" therefore holds because nothing renders red; the new grey dormant row is currently the only styled health state. Worth knowing before someone reads D13 as having established an alarm palette.
11. **File size.** `cueEngineService.js` is now 1,181 lines (+312) and `commandExecutor.js` 1,055 (+119). Neither was created by this task, but the dormancy sweep + the three sets + the three-valued fire is a coherent collaborator that could live beside `cue/standingEvaluator.js` if the file grows again.
